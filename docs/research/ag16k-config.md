## 0. 要約

1. **AG16KDDF256 は「AG16K FPGA + DDR-SDRAM の積層品」で、資料上フラッシュは入っていない** [一次：AGM の DDF256 マニュアル]。
   AS（マスター）は外付け SPI フラッシュを前提にしていて、そのための 4 本（ASDO / NCSO / DCLK / DATA0）がボールに出ている。
   基板に外付けフラッシュが無い（R6）以上、**R41 の推定（MCU が PS で流す）は資料と整合する**。残る別解は「MCU か外部ケーブルが JTAG で流す」だけ。
2. **モード選択は MSEL1 の 1 本だけ**（MSEL2・MSEL0 はパッケージ内で GND）。**MSEL1 = 0 が PS、1 が AS**、JTAG はどちらでも使える [一次]。
3. **コンフィグ用のボールが分かった** [一次：同マニュアルのボール表]。
   DCLK = **G1**、DATA0 = **G2**、NCONFIG = **H3**、NSTATUS = **F3**、CONF_DONE = **F16**、MSEL1 = **F15**、TDI/TCK/TMS/TDO = **H1 / H2 / J1 / J2**。
   **`g1-ag16k-port.md` §2-4 が Cyclone IV の記憶から書いた候補（F4・H1・H2・H5・H14…）は DDF256 には当てはまらない。**
   DDF256 は EP4CE15F17 とピン互換ではない（互換なのは DDR なしの F256 と、SDRAM 版の SDF256）。
4. **PS に流すファイルは `<design>.bin` か `.rbf`**。`.rbf` は `.bin` の各バイトのビット順を反転したもの [一次]。
   線に出る順は「`.bin` を MSB 先頭」＝「`.rbf` を LSB 先頭」と見られる [推測。根拠は §2-3]。
   **今の `cyclone.rs`（LSB 先頭）には `.rbf` をそのまま渡せばよい**見込み。外れても、ファイルを取り替えるだけで直る。
5. **AG16K は PS でも圧縮ビットストリームを受け付ける**（AG10K の旧品は不可）[一次：AGM の AG10K/16K 設計ガイド]。圧縮は LZW [一次：rodinia]。
6. **PS のタイミング値（nCONFIG の幅、nSTATUS の待ち、DCLK の上限、CONF_DONE 後のクロック数）は AGM の資料のどこにも無い** [一次：4 つの資料を全文検索]。
   Cyclone IV E の値を出発点にし、余裕を大きく取る。純正の波形を 1 回記録すれば全部埋まる（`g1-ag16k-port.md` §1-5）。
7. **流す時間の見積もり**（非圧縮 552,366 B = 4,418,928 bit、MCK 96 MHz）：今のループのままで **2.2〜3.3 秒**、
   待ちの NOP を外して **0.7〜1.2 秒**、ポートへの書き込みを 1 bit あたり 2 回にまとめて **0.5〜0.9 秒** [推測。測っていない]。

## 1. コンフィグ方式とピン

### 1-1 方式と MSEL

| 項目 | 内容 | 根拠 |
|------|------|------|
| 方式 | JTAG、AS（Master）、PS（Slave）。SDRAM 版のマニュアルには Fast AS も載る | [一次] `MANUAL_AG16KDDF256.pdf` p.4、`MANUAL_AG16KSD.pdf` p.21 |
| MSEL | DDF256 は **MSEL[2] と MSEL[0] がパッケージ内で GND**。外に出ているのは MSEL1 だけ | [一次] DDF256 マニュアル p.4 |
| MSEL1 の値 | **AS = 1、PS = 0、JTAG = 0/1（どちらでも可）** | [一次] 同上の表 |
| 3 本そろった品での値 | MSEL[0..2] は AS で `010` または `101`、PS で `000`。**抵抗を挟まず VCC / GND に直結する**（抵抗があると Supra からのフラッシュ書き込みが失敗しうる） | [一次] `AG10K_16K_guide.pdf` §15 と p.4 |
| Cyclone IV E との関係 | MSEL1 だけで AS / PS が切り替わる点は `g1-ag16k-port.md` §1-3 の類推（Low = PS、High = AS）と一致 | [一次] で確定 |

読み取れること：

- **nCE、nCEO、INIT_DONE、CRC_ERROR、MSEL0、MSEL2 に当たるボールは無い** [一次：ボール表に出てこない]。チェーン接続や INIT_DONE の監視は考えなくてよい。
- **電圧**：コンフィグ用のボールは I/O バンクの中にあり、そのバンクの VDDIO（3.3 / 2.5 / 1.8 V）で動く [推測。Cyclone IV と同じ作りなら]。
  DCLK・DATA0・NCONFIG・NSTATUS・JTAG は左辺のバンク（表の VDDIO1）、MSEL1・CONF_DONE は右辺のバンク（VDDIO5）の領域にある [一次：ボール表の色分け]。
  6.0 の基板は MCU が 3.3 V なので 3.3 V と見るが、VDDIO1 と VDDIO5 の電圧は基板で確かめる。
- **プルアップ**：CONF_DONE の 1 kΩ は Cyclone（10 kΩ）より強い。`cyclone.rs` は MCU の内蔵プルアップ（数十 kΩ）を有効にしているが、
  マニュアルどおりの基板なら外付けがあり、内蔵は無くても動く。逆に外付けが無い基板だと、内蔵だけでは立ち上がりが遅いおそれがある。**基板に 1 kΩ / 10 kΩ があるかを見る**（§7）。

### 1-4 PS の手順とタイミング

**AGM の資料に、PS の波形・手順・タイミング値は載っていない。** 読んだのは DDF256 マニュアル（9 ページ）、SD 版マニュアル（27 ページ）、
AG10K/16K 設計ガイド（9 ページ）、Supra マニュアル 6.2（16 ページ）、AG16K PSoC データシート（R32 で既読）。
どれも「PS に対応、ファイルは .bin / .rbf」としか書いていない [一次]。

AGM の品は Cyclone IV 互換を売りにしていて（開発手順が Quartus の EP4CE15 を土台にする、ピン名が同じ、USB-Blaster をそのまま使う、JTAG の命令長が同じ 10 bit）、
PS の作法も Cyclone IV E に合わせてあると見るのが自然 [推測]。出発点にする Cyclone IV E の値：

| 記号 | 意味 | Cyclone IV E の値 | AG16K での扱い |
|------|------|-------------------|----------------|
| tCFG | nCONFIG を Low に保つ時間 | 500 ns 以上 [記憶] | 1 ms（今の値のまま） |
| tCF2ST0 | nCONFIG Low → nSTATUS Low | 500 ns 以下 [記憶] | Low を確認してから進む（上限 10 ms） |
| tSTATUS | nSTATUS の Low パルス幅 | 45〜230 µs [二次：Intel の表の検索要約。品種は未確認] | — |
| tCF2ST1 | nCONFIG High → nSTATUS High | 230 µs 以下 [記憶] | **上限 500 ms で待つ**（電源投入直後は POR の時間が加わる。AGM の POR 時間は [不明]） |
| tST2CK | nSTATUS High → 最初の DCLK 立ち上がり | 2 µs 以上 [記憶] | 50 µs 待つ |
| tDSU / tDH | DCLK 立ち上がりに対するデータのセットアップ / ホールド | 5 ns / 0 ns [記憶] | GPIO の書き込み 1 回分（10 ns 以上）で足りる |
| tCH / tCL | DCLK の High / Low 幅 | 各 3.2 ns 以上 [記憶] | 各 30 ns 以上を目標にする |
| fMAX | DCLK の上限 | 133 MHz [記憶。Altera の KB が Cyclone IV の DCLK 133 MHz に触れている＝二次] | ビットバンは 10 MHz に届かない。上限は問題にならない |
| — | CONF_DONE が上がった後に要るクロック | **DCLK の立ち下がり 2 回**で初期化が始まる [記憶] | **余分に 64 クロック送る**（多くて困ることはない） |
| tCD2UM | CONF_DONE High → ユーザーモード | 300〜650 µs [記憶] | 今の 10 ms 待ちのままで足りる |
| — | データの向き | DCLK の立ち上がりで取り込み。各バイト LSB 先頭 | §2-3 |

[記憶] の値は Cyclone IV Device Handbook 第 1 巻・コンフィグの章（CYIV-51008）の「PS Timing Parameters」の表にある。
今回は Intel のサイトの移転で原典を開けなかった（404 / 410 / 403）。**実装の前に原典で確かめること。**
ただし下の設計は、どの値にも 10 倍以上の余裕を取っているので、多少の記憶違いは結果に響かない。

AGM 側で分かっている、手順に関わる事実：

- **「FPGA の論理はすべて、コンフィグ完了（conf_done が High）の後に動き始めること」** [一次：設計ガイド §8]。CONF_DONE が完了の合図であることは Cyclone と同じ。
- **コンフィグ成功の時点で PLL はロック済みで、lock はすでに High**。lock をリセットに使う設計は電源投入リセットがかからない [一次：同 §1]。
  NetGD の `Audio_PLL` の lock をリセットに使っていないかを確かめる（FPGA 側の話。ローダには関係しない）。
- **専用クロック入力には内部プルアップが無く、開放だと 0 に見える**（EP4C は 1）[一次：同 §6]。
- **3.3 V の VCCIO は、1.2 V と 2.5 V より遅れずに立ち上げる** [一次：同 §12]。理由はコンフィグ用フラッシュの起動待ちなので、PS では効かないはずだが、純正基板はこの順になっていると見てよい。
- **コンフィグ用の内蔵発振器の速さは `.asf` の `OSC_FREQUENCY`（0 = 最も遅い〜7 = 最も速い）で変えられる** [二次：販売店 hizyuan の事例記事]。AS のクロックの話で、PS では外から DCLK を与えるので関係しない。
- **コンフィグ中のユーザー I/O の状態**（弱いプルアップか、ハイインピーダンスか）は [不明]。G1 バスへの影響があるので、最初の実機確認で測る（`g1-ag16k-port.md` §2-5 と同じ）。

## 2. Supra が出すファイルと、PS に流すもの

### 2-1 ファイルの種類

| ファイル | 用途 | 根拠 |
|----------|------|------|
| `<design>.bin` | **基本のコンフィグファイル。ほかの形式の元。PS にも使う** | [一次] Supra マニュアル 6.2 §4 |
| `<design>.rbf` | **`.bin` の各バイトの上位・下位ビットを反転したもの。PS 用** | [一次] 同上、DDF256 マニュアル p.9 |
| `<design>_SRAM.prg` | JTAG で FPGA の SRAM に直接書く。電源を切ると消える。デバッグ用 | [一次] |
| `<design>_master.prg` | AS のとき、JTAG 経由で**外付け**コンフィグ用フラッシュに書く。書く前にフラッシュの消去が要る | [一次] |
| `<design>_master.bin` | AS のとき、フラッシュライタで書く標準イメージ | [一次] |
| `<design>_master_as.prg` | 上の `.bin` を AS ポートから直接書く | [一次] |

`.prg` は `sir` / `sdr` / `runtest` を並べたテキストの JTAG スクリプト [一次：`rodinia/bitstream/bin2prg.py` が出す形]。

### 2-2 `.bin` の中身 [一次：`rodinia/bitstream/agm-unpack.py`・`chips.py`]

| 位置 | 内容 |
|------|------|
| 先頭 16 bit | `ff55`（AG16K の SPI フラッシュ用で観測）、`5555`（AG10K）、`ffff`（AG1K）。`ff55` / `5555` の後には 12 バイトの決まった並び `00 00 0e 00 …00` が続く |
| 次の 32 bit | `967e3c5a`（AG16K で観測。用途不明。無い品もある） |
| 次の 32 bit | デバイス ID。**`0x01500010`**（rodinia の内部名は `AG15K`、パッケージ名は `AG16KSDE176`）。AG10K は `0x01000001` |
| 次の 32 bit | `0000FFFF`（意味は不明） |
| 次の 1 バイト | **`0x55` なら以降が LZW 圧縮**。32 bit 境界まで飛ばして、残り全部が LZW のデータ |
| 以降 | 32 bit 語の列。`0x2A…` = レジスタ書き込み（宛先 `0x00000F8F` への書き込みが CRC の値）、`0xA2…` = 配列（タイル列、またはコンフィグチェーン）、`0x22…` = 不明 |

- **大きさ**：非圧縮で 552,366 B（rodinia の `blinky16k.bin`。R32 で確認済み）。DDF256 は同じ AG16K のダイに DDR を重ねたものなので、同じ大きさになるはず [推測]。
- **LZW の設定**：AG16KSDE176 は `lzw_length: 8`、`variable_width: True`。AG10K は `lzw_length: 6`、固定幅 [一次：`chips.py`]。
- **rodinia が展開できるのは AG16KSDE176 の非圧縮だけ**（README）。DDF256 のピン名の表は持っていない。大きさの確認と先頭部の検査には使える。
- **CRC**：ストリームの中に CRC の値がある。FPGA がそれを検査して、合わなければ nSTATUS を下げるかどうかは [不明]（Cyclone は下げる）。

### 2-3 どのファイルを、どの向きで流すか

事実：
- PS に使うのは `.bin` か `.rbf`、`.rbf` は `.bin` のビット順を反転したもの [一次]。
- SPI フラッシュ用の `_master.bin` について、設計ガイドは「Altera の POF 系のファイルは MSB-LSB が逆なので、反転してから書く」と注意している [一次：§4]。
  つまり **AGM のファイルは、SPI フラッシュが読み出す向き（各バイト MSB 先頭）でそのまま並んでいる**。Altera の `.rbf` は逆で、各バイト LSB 先頭で線に出る。
- `bin2prg.py` の SRAM 用の経路は、`.bin` の先頭 8 バイトと末尾 4 バイトを落とし、**バイトの並びもビットの並びも全部ひっくり返して** 1 本の `sdr` にしている [一次]。
  JTAG は最下位ビットから送るので、線に最初に出るのは「`.bin` の最初のバイトの MSB」になる。

ここから：**FPGA が受け取る順は「`.bin` を各バイト MSB 先頭」。`.rbf` はそれを Altera 流（各バイト LSB 先頭）で送れるようにした変換** [推測。3 つの事実が同じ向きを指す]。

→ **`cyclone.rs` は今 LSB 先頭で送っているので、`build.rs` が読むファイルを `.rbf` にすれば、送る側は変えなくてよい。**
  `.bin` を使うなら MSB 先頭で送る。**どちらが正しいかは実機で 1 回試せば分かり、間違っても壊れない**（CONF_DONE が上がらないだけ）。
  間違いに早く気づけるよう、ビット順はローダの設定値にしておく（§6）。

PS で SPI フラッシュ用の先頭部（`ff55` と 12 バイト）をそのまま流してよいかは [不明] だが、Supra マニュアルが「`.bin` は PS にも使う」と書いているので、**ファイルを加工せず丸ごと流す**のが素直な読み方 [推測]。

### 2-4 圧縮

| 項目 | 内容 | 根拠 |
|------|------|------|
| AS での圧縮 | AG10K / 16K とも対応。設計によって大きさが変わる | [一次] 設計ガイド §10 |
| **PS での圧縮** | **AG16K は対応**。AG10K の旧品は非対応（AG10KL144H は対応） | [一次] 同上「AG16K 支持 PS 压缩」 |
| 切り方 | `.asf` に `set_global_assignment -name ON_CHIP_BITSTREAM_DECOMPRESSION OFF`。Quartus 側で圧縮を選んでいると、それが引き継がれる | [一次] 同上 |
| 方式 | LZW（符号長 8 bit から、可変幅） | [一次] rodinia |
| NetGD の設計での大きさ | **[不明]**。Supra で 1 回ビルドすれば基板なしで分かる | — |

**フラッシュの大きさと流す時間は、逆の向きに効く：**

| 埋め込む形 | フラッシュ上の大きさ | 流すビット数 | 見込み |
|------------|----------------------|--------------|--------|
| 非圧縮 `.rbf` を LZMA | 55〜75 KB [R32 の推測]。下限は空の設計の 10.4 KB [測定：R32] | 4,418,928（固定） | 大きさは最小。流す時間は §4-3 の手当てで 1 秒前後にできる |
| AGM 圧縮（LZW）の `.rbf` を LZMA | LZW の出力は LZMA でほとんど縮まないので、**LZW 後の大きさがほぼそのまま**載る [推測]。67 KB の上限に入るかは [不明] | LZW 後の大きさ × 8 | 流す時間は最短。入るかどうかが問題 |
| AGM 圧縮の `.rbf` を生で置く | 同上 | 同上 | LZMA の展開が要らなくなる。大きさが許せば最も単純 |

→ **Supra が手に入ったら、圧縮あり / なしの両方を出して 3 つの数字（非圧縮→LZMA、LZW、LZW→LZMA）を取る**（`g1-ag16k-port.md` §3-2 の測定に 1 行足すだけ）。
  v5.5 で「Quartus の圧縮は切らない」と決めたのと同じ判断を、AG16K の数字でやり直すことになる。

## 3. 「M なし」の品に内蔵フラッシュはあるか（R41 の推定の検証）

| 根拠 | 内容 | 種別 |
|------|------|------|
| DDF256 マニュアル p.2 | 「AG16KDDF256 は AGM FPGA AG16K と DDR-SDRAM を積層して集積したチップ」。構成要素として挙げているのは FPGA と DDR だけ | [一次] |
| 同 p.3 | SPI の 4 本（ASDO / NCSO / DCLK / DATA0）がボールとして外に出ていて、通常の I/O にも使える。内蔵フラッシュなら外に出す理由が薄い | [一次] |
| 同 p.4 | 「AS 方式では JTAG 口から配置 FLASH を直接書くこともできる」。フラッシュは FPGA の外にあるものとして書かれている | [一次] |
| Supra マニュアル §4 | AG10K / 16K 系の `_master.prg` は「JTAG 経由で**外部**コンフィグ用フラッシュに書くファイル」 | [一次] |
| 設計ガイド §12 | 「コンフィグ用フラッシュ（3.3 V）が先に起動するよう、3.3 V を先に立ち上げる」。別部品としての扱い | [一次] |
| PSoC データシート（R32） | 「プロセッサ・FPGA・SDRAM/DDR・ADC・Flash を 1 チップに」と書くのは、型番が `…M` で終わる品（AG16KDDF256**M** など） | [一次] |

**結論：`AG16KDDF256`（M なし）は FPGA + DDR だけで、コンフィグ用フラッシュも MCU も入っていない、と読むのが資料に最も合う。R41 の推定は支持される** [一次の組み合わせからの推測]。
言い切れない点：マニュアルに「フラッシュは無い」と明記した文は無い。M が何を指すか（MCU とフラッシュを足した品、と読める）を定義した文も見つかっていない。

`g1-ag16k-port.md` の分岐への影響：

- **分岐 B1（内蔵フラッシュから自分で起動）は、ほぼ成り立たない。** 基板に外付けフラッシュが無く、パッケージにも無いなら、FPGA が自分で読む先が無い。
- 残るのは **A / A'（MCU が PS で流す）** と、新しく **A''（MCU が JTAG の 4 本で流す）**。A'' は珍しいが、導通確認で JTAG のボール（H1 / H2 / J1 / J2）が MCU に行っていれば成り立つ。
- **MSEL1（F15）が GND なら PS で確定**。3.3 V につながっていたら AS なので、どこかにフラッシュがあることになり、上の結論が崩れる。**MSEL1 の電位が最も安い判定材料**（§7）。

### 4-3 流す時間の見積もり（測定ではない）

前提：MCK = PLLA = 96 MHz（`clocks.rs`）。非圧縮 552,366 B = **4,418,928 bit**。
GPIO への 1 回の書き込みは、定数の読み込みを含めて 3〜5 サイクル [推測]。NOP は 1 個 1 サイクル。

| 送り方 | 1 bit あたり | 速さ | ビットバンの時間 | LZMA の展開 | 合計 |
|--------|-------------:|-----:|----------------:|------------:|-----:|
| **今のループのまま**（NOP 20 個 + ループの枝 + GPIO 3 回 + バイトごとの検査） | 45〜60 サイクル | 1.6〜2.1 Mbit/s | 2.1〜2.8 秒 | 0.1〜0.5 秒 | **2.2〜3.3 秒** |
| **待ちの NOP を外す**（GPIO 3 回のまま） | 12〜16 サイクル | 6〜8 Mbit/s | 0.55〜0.75 秒 | 同上 | **0.7〜1.2 秒** |
| **1 bit を 2 回の書き込みにする**（DATA と DCLK=Low を 1 回で出し、次に DCLK=High。PA23 と PA24 は同じポートなので、PIO_OWER で 2 本だけを PIO_ODSR の書き込み対象にすれば 1 回で両方変えられる） | 8〜10 サイクル | 10〜12 Mbit/s | 0.37〜0.46 秒 | 同上 | **0.5〜0.9 秒** |
| 参考：v5.5 の今（590,568 bit） | 45〜60 サイクル | 同上 | 0.28〜0.37 秒 | 小 | 0.3〜0.6 秒（R32 の目安と同じ） |

補足：

- **LZMA の展開時間は幅が大きい。** 文字 1 個（literal）の展開は 200〜400 サイクル、一致（match）の複写は 1 バイトあたり十数サイクル [推測]。
  AG16K の非圧縮ストリームは大半が 0 の繰り返しで（空の設計が 552 KB → 10.4 KB に縮む [測定：R32]）、ほとんどが一致の複写になる。
  NetGD の設計の情報量を 45〜65 KB とすると、0.1〜0.5 秒。
- **0 のバイトの近道**：値が 0 のバイトでは DATA を動かす必要が無く、DCLK を 8 回上下させるだけでよい。非圧縮ストリームの大半がこれに当たる。
- **AGM 圧縮を使えば、流すビット数そのものが減る。** たとえば LZW 後が 150 KB なら 1.2 Mbit で、今のループのままでも 0.6〜0.8 秒。大きさは [不明]。
- **周辺機能に送らせる案**（USART の同期モードや SPI）は、DATA0 / DCLK のピンがその機能に割り当てられる場合だけ使える。
  PA23 / PA24 の代替機能は今回確かめていない（`g1-ag16k-port.md` §3-4 と同じく未確認）。上の 3 段目で 1 秒を切る見込みなので、優先度は低い。
- **DCLK の波形**：3 段目では DCLK の High 幅が 30〜50 ns まで短くなる。Cyclone IV の下限（3.2 ns [記憶]）よりずっと長いが、
  基板の配線と直列抵抗しだいで波形が鈍る。**最初は 2 段目（NOP なし）で動かし、動いてから 3 段目を試す。**
- **Dreamcast がどこまで待てるかは未測定**（`g1-ag16k-port.md` U10）。純正が何秒で流しているかを波形で見れば、それが実績のある上限になる。

## 5. JTAG を使う別の道

| 項目 | 内容 | 根拠 |

| ボール | TDI = H1、TCK = H2、TMS = J1、TDO = J2 | [一次] §1-3 |
| 推奨回路 | Altera の USB-Blaster と同じ（TCK は 1 kΩ で GND へ、TMS / TDI は 10 kΩ で VCC へ）。10 ピンでない独自のヘッダでは 2 番と 10 番を GND に | [一次] Supra マニュアル §5 |
| メーカーの道具 | Supra の Tools → Program。ケーブルは USB-Blaster（互換品）か AGM DAP-LINK。`Query` でデバイス ID が読める | [一次] Supra マニュアル §4 / [二次] hizyuan |

| JTAG の命令 | 命令レジスタ 10 bit。フラッシュ操作は `0x3F8`〜`0x3FD`。SRAM 用の経路は `sdr` 1 本（`.bin` の先頭 8 バイト・末尾 4 バイトを除いて全ビット反転）で、直前の命令は `bin2prg.py` には書かれていない | [一次] rodinia `bin2prg.py` |
| オープンなツール | **openFPGALoader・OpenOCD が AGM の AG10K / AG16K に対応しているという情報は見つからなかった**（検索 1 回。無いことの証明ではない） | [二次] |
| オープンなツールで書く道筋 | (a) Supra で `_SRAM.prg` を作る（または `bin2prg.py` で `.bin` から作る）→ (b) `.prg` の `sir` / `sdr` / `runtest` を SVF に書き換える → (c) OpenOCD の `svf` で流す。**誰かが通した記録は見つかっていない** | [推測] |

6.0 の基板での位置づけ：

- **書き込みの手段としては要らない。** フラッシュが無いので、JTAG で書いても電源を切れば消える。毎回の起動は MCU が担うしかない。
- **調査の手段としては役に立つ。** 8 ピンヘッダが FPGA の JTAG なら、(1) デバイス ID の読み出しで FPGA が生きているかを見る、
  (2) MCU を ERASE する前に、`_SRAM.prg` でピン探索用ビットストリーム（`g1-ag16k-port.md` §2-4 の方法 2）を流す、
  (3) PS ローダが動かないときに、ビットストリーム自体は正しいかを切り分ける、の 3 つに使える。
  (2) は「純正を消す前に自前のビットストリームを試せる」という意味で価値が大きい。ただし純正 MCU が動いたままだと、SMC のピンが衝突しうるので、探索用は全ピン入力のものに限る。
- **MCU が JTAG で流す構成（A''）**：H1 / H2 / J1 / J2 が MCU のピンに行っている場合。そのときは PS ローダではなく JTAG のビットバン（TAP の状態遷移 + `sdr` 1 本）を書くことになる。
  SRAM 用の `sdr` の前に要る命令が `bin2prg.py` から読み取れないので、Supra が出す `_SRAM.prg` の実物を見てから設計する。**導通確認でこの形だと分かるまで、手を付けない。**

## 6. `cyclone.rs` の変更一覧（設計。コードではない）

ファイル名は `g1-ag16k-port.md` §4-3 の案（`fpga_loader.rs` に改名、`PsProfile` を導入）に合わせる。
**v5.5（Cyclone II）向けのバイナリが変更の前後で一致すること**を条件にするなら、下の変更はすべて `PsProfile` の値で切り替え、Cyclone II の値は今の動作そのままにする。

**(1) `PsProfile` に持たせる値**

| 値 | Cyclone II（今の動作） | AG16K（初期値） | 理由 |
|----|------------------------|-----------------|------|
| ビット順 | LSB 先頭 | LSB 先頭（`.rbf` を使う前提） | §2-3。逆だったら `.bin` に替えるか、この値を変える |
| nCONFIG の Low 時間 | 1 ms | 1 ms | Cyclone IV の下限 500 ns [記憶] の 2,000 倍 |
| nSTATUS が Low になるのを待つ上限 | 待たない | 10 ms（Low を確認できなくても先へ進み、記録だけ残す） | やり直しのとき、FPGA がリセットを受け付けたことの確認 |
| nSTATUS が High になるのを待つ上限 | 無限 | 500 ms | POR の時間が [不明] なので長めに |
| nSTATUS High → 最初のクロックの待ち | 0 | 50 µs | Cyclone IV の下限 2 µs [記憶] |
| 1 bit あたりの待ち | NOP 5 個 × 4 | 0（段階 2）。動いたら段階 3 の送り方へ | §4-3 |
| CONF_DONE 後の追加クロック | 0 | 64 | Cyclone IV は立ち下がり 2 回 [記憶]。AGM は [不明] なので多めに |
| データを送り切った後、CONF_DONE を待つ追加クロックの上限 | 無限 | 4,096 | 無限ループをやめる |
| やり直しの回数 | 0（`panic!`） | 3 | nSTATUS が落ちたとき、CONF_DONE が来ないとき |
| 終了時の DCLK / DATA0 | High / 最後の値 | Low / Low | 決まった状態で止める |
| CONF_DONE 後、ユーザーモードまでの待ち | 10 ms | 10 ms | 今の `main.rs` の値 |

**(2) `load_from` の流れ**

1. nCONFIG を Low にして所定の時間待つ（今は `new()` の初期値に頼っている。やり直しのために、関数の中で明示的に Low にする）。
2. nSTATUS が Low になったことを上限つきで確かめる。
3. nCONFIG を High にし、nSTATUS が High になるのを上限つきで待つ。上限を超えたら「nSTATUS が上がらない」で失敗。
4. 所定の時間待ってから、データを送る。1 バイトごとに nSTATUS を見て、Low なら「途中でエラー」で失敗（何バイト目かを添える）。
5. **CONF_DONE が High になったら、データの残りは捨てて、追加クロックへ進む**（今は即 `return`）。
6. データを送り切っても CONF_DONE が Low なら、上限まで 0 を送る。上限を超えたら「CONF_DONE が上がらない」で失敗。
7. 追加クロックを送り、DCLK と DATA0 を Low にして成功を返す。
8. 戻り値は `Result<LoadStats, PsError>`。`LoadStats` には送ったバイト数とやり直しの回数、`PsError` には上の 3 種類と「展開の失敗」を入れる。`panic!` は無くす。

**(3) やり直しと反復子**

- やり直すにはビットストリームを先頭から読み直す必要がある。今の `load_from` は反復子を 1 つ受け取るだけなので、
  **「反復子を作る関数」を受け取る形**にする（LZMA の展開器は作業領域を借り直して作り直せる。`main.rs` の `dec.error()` の検査は 1 回ごとに行う）。
- 3 回とも失敗したら、`main.rs` は止まって LED の点滅回数で種類を示す（1 回 = nSTATUS が上がらない、2 回 = 途中でエラー、3 回 = CONF_DONE が上がらない、4 回 = `0xC0DE` が読めない）。
  `DEFMT_LOG=off` ではログが出ないので、LED が唯一の手がかりになる（R32 のリスク R11）。

**(4) ピンの受け渡し**

- `PSLoader::new` はすでにピンを型引数で受け取っているので、ローダ側の変更は要らない。変えるのは渡す側（`UserPeripherals` の固定をやめ、`board/v55.rs`・`v60.rs` が選ぶ。`g1-ag16k-port.md` §4-3 のとおり）。
- 段階 3 の送り方（ポートへの直接書き込み）は「DCLK と DATA0 が同じポート」が条件。`PsProfile` ではなく、ボード定義が「速い送り方が使える」と申告する形にする。条件を満たさないボードは段階 2 のまま。
- 入力 2 本の内蔵プルアップは今のまま有効にしておく（外付けがあれば無害、無ければ最低限の保険）。

**(5) `build.rs` と `main.rs`**

- `build.rs`：`RBF` を `board-v60` のとき `fpga/agm/output/OpenGDEMU.rbf` にする（`g1-ag16k-port.md` は `.bin` と書いているが、§2-3 の理由で `.rbf` を既定にする。両方コミットしておけば切り替えは 1 行）。
  ビルド時に、ファイルの先頭 2 バイトが `ff 55` のビット反転（`ff aa`）であることを確かめ、違えば警告を出す（`.bin` と `.rbf` の取り違えの検出）[推測に基づく検査。実物の `.rbf` で先頭を確かめてから入れる]。
- `main.rs`：`BITSTREAM_RAW_LEN` が 7.5 倍になるだけで、LZMA の作業領域（約 7.6 KB）は変わらない。
  「FPGA Loaded! (… ms)」の値を、ログが切れていても読めるようにする（FPGA のレジスタか、ATAPI 経由のログ読み出し＝R17 に載せる）。G1-4 の「起動までの時間」の記録に使う。

**(6) 試験（実機なしでできる範囲）**

- ホスト側のテストで、ピンの代わりに記録器を渡し、(a) ビット順、(b) CONF_DONE の後に追加クロックがちょうど所定の数だけ出ること、(c) nSTATUS を途中で落とすとやり直すこと、
  (d) どの失敗でも上限で必ず戻ること、を確かめる。今の `cyclone.rs` は `embassy_atsam3` の型に直接依存しているので、ピン操作を小さなトレイトに切り出すところから始める。
- Cyclone II のプロファイルで、変更前と同じ波形（記録器の出力）になることを確かめる。

## 7. 導通確認で見てほしいところ（持ち主への質問）

作業 2（`docs/research/user-tasks.html`）に足す項目。**部品を上から見て、1 番ピンの印（丸印）がある角が A1**。
行は印の角から縦に A, B, C, D, E, F, G, H, J, K, L, M, N, P, R, T、列は横に 1〜16。BGA のボールには直接触れないので、
ボールのすぐ外に出ている配線・ビア・抵抗に当てる。左端の列（G1・H1・J1）と右端の列（F16）は最外周なので、表面の配線で追いやすい。

| # | 当てる場所（MCU 側） | 当てる場所（FPGA 側） | 分かること |
|---|----------------------|------------------------|------------|
| Q1 | — | **F15（MSEL1）と GND**、F15 と 3.3 V | **GND に導通 → PS で確定（最重要）。** 3.3 V に導通 → AS（どこかにフラッシュがある）。右端から 2 列目、上から 6 行目 |
| Q2 | PA24（105 番） | **G1（DCLK）** 付近の配線 | 分岐 A の直接の証拠。左端の列、上から 7 行目 |
| Q3 | PA23（103 番） | **G2（DATA0）** | 同上 |
| Q4 | PA25（106 番） | **H3（NCONFIG）** | 同上。近くに **10 kΩ のプルアップ**があるはず |
| Q5 | PB2（57 番） | **F3（NSTATUS）** | 同上。10 kΩ のプルアップ |
| Q6 | PB1（55 番） | **F16（CONF_DONE）** | 同上。**1 kΩ のプルアップ**（3.3 V との間が約 1 kΩ） |
| Q7 | MCU の全ピン（電源以外）を順に | H1 / H2 / J1 / J2（TDI / TCK / TMS / TDO）につながる配線 | MCU に行っていれば分岐 A''。**ヘッダ（8 ピンが候補）に行っていれば FPGA の JTAG ヘッダ** |
| Q8 | 8 ピンヘッダの各ピン | GND、3.3 V、1 kΩ で GND に落ちているピン（= TCK の候補）、10 kΩ で 3.3 V に上がっているピン（= TMS / TDI の候補） | JTAG ヘッダかどうかの見当 |
| Q9 | PA21（102 番）と PA28（45 番） | 専用クロックのボール（J4、K1、L1、G15、G16、H15、H16、E9、F9、R14、T14）付近 | 48 MHz がどのクロック入力に来ているか（R32 で追加済みの項目に、行き先の候補を足す） |
| Q10 | 74HC04D の出力 | 同じ専用クロックのボール | 11.2896 MHz の行き先。**PLL は同じ辺のクロックピンからしか入力できない**ので、どの辺かが FPGA の設計を縛る |
| Q11 | — | 基板上の 2.5 V と 1.25 V（レギュレータの出力） | DDR 用の電源があるか。あれば DDF256 のマニュアルどおりの基板 |
| Q12 | — | C1（ASDO）・D2（NCSO）付近 | どこにもつながっていなければ、AS は使われていない（PS の傍証） |

Q2〜Q6 の MCU 側のピン番号は `user-tasks.html` の表のもの。**PA23 / PA24 / PA25 / PB1 / PB2 が当たらなかったら、G1・G2・H3・F3・F16 の側から MCU の全ピンを当たる**（分岐 A'）。

電源を入れて測れるなら（Dreamcast に挿した状態、読み取りだけ）：

| # | 測るもの | 分かること |
|---|----------|------------|
| Q13 | 電源投入から、DCLK（PA24 か G1 の配線）にクロックの束が出ている時間 | 純正が流している時間 = Dreamcast が待てることが実証済みの長さ |
| Q14 | ロジアナがあれば DCLK と DATA0 の 2 本を、電源投入から CONF_DONE が上がるまで記録 | クロック数（= ビット数。4,418,928 なら非圧縮、少なければ圧縮）、DCLK の周波数、ビット順（先頭が `ff 55` の MSB 先頭か LSB 先頭か）、CONF_DONE 後のクロック数。**§1-4 の [不明] と [記憶] がほぼ全部埋まる** |
| Q15 | nSTATUS と nCONFIG の電源投入時の波形 | POR の長さ、nCONFIG を Low にしている時間 |

Q14 で記録したビット列は純正のビットストリームそのものなので、リポジトリには置かない（`g1-ag16k-port.md` §1-5 と同じ扱い）。数（ビット数・周波数・時間）だけを記録に残す。

## 8. リスク

| # | リスク | 影響 | 手当て |
|---|--------|------|--------|
| C1 | **PS の作法が Cyclone IV と違う**（追加クロックの数、nSTATUS の意味、先頭部の扱い） | CONF_DONE が上がらない | 値を `PsProfile` に出しておく。Q14 の波形があれば純正をそのまま真似る。JTAG の `_SRAM.prg` で「ビットストリームは正しい」を先に切り分ける |
| C2 | **ビット順の読みが逆**（§2-3 は推測） | 同上 | `.bin` と `.rbf` の両方を用意し、1 回ずつ試す。壊れる操作ではない |
| C3 | **ボール表の読み違い**（画像を目で読んだ。原本は透かし入りの写し） | 導通確認で当たる場所がずれる | Q1〜Q6 の結果と突き合わせる。5 本とも合えば表は正しい |
| C4 | **非圧縮で流す時間が長い**（今のループのままで 2〜3 秒） | Dreamcast が GD-ROM を見失うおそれ | §4-3 の段階 2・3、または AGM 圧縮。Q13 で純正の時間を知る |
| C5 | **AGM 圧縮のビットストリームが 67 KB に入らない** | 圧縮で時間を縮める道が使えない | 非圧縮 + LZMA + 速いビットバンで行く。Supra での実測が先 |
| C6 | **速いビットバンで DCLK の波形が崩れる** | ときどき失敗する | 段階 2 で安定させてから段階 3 へ。やり直し 3 回で一時的な失敗を吸収する。失敗回数を記録に残す |
| C7 | **MSEL1 が AS 側（3.3 V）だった** | §3 の結論が崩れる。隠れたフラッシュがあるか、基板が想定と違う | Q1 を最初にやる。AS 側でも JTAG の SRAM 書き込みは使えるが、MCU からの PS は MSEL1 を GND に落とす改造が要る |
| C8 | **コンフィグ線が MCU ではなく JTAG で来ている（A''）** | PS ローダが使えない。JTAG のビットバンを別に書く | Q7。分かるまで手を付けない |
| C9 | **コンフィグ後、DCLK / DATA0 のボールが通常の I/O になる** | FPGA の設計がこの 2 本を出力にすると、MCU の出力とぶつかる | NetGD の設計では G1・G2 を未使用（入力）に固定する。ローダは終了時に両方 Low で止める |
| C10 | **DDR 用の 2.5 V / 1.25 V が基板に無い、または DDR を放置したときの挙動** | 不安定、余分な電流 | Q11。使わない DDR の止め方はマニュアルに記述が無い [一次：全文を確認]。純正も DDR を使っていない可能性がある（GDEMU の機能に 128 Mbit の RAM は要らない）[推測] |
| C11 | **Cyclone IV の値を [記憶] で書いた** | 余裕の取り方を誤る | 実装の前に CYIV-51008 の表で確かめる。設計上の値はどれも 10 倍以上の余裕 |
| C12 | **nSTATUS の待ちに上限を入れたことで、POR が長い個体で失敗する** | 起動しない | 上限は 500 ms と長めにし、失敗してもやり直す。Q15 で実際の長さを見る |
