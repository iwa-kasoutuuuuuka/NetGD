# G3-4：CD_READ から SD までの読み出し経路と高速化

担当：Sonnet 5.5（調査・実装）。Opus による検証：**未**。実機での検証：**なし**（ここにある数値は、クロックとコードから出した見積もりで、実機の計測値ではない）。
コミット前の作業ツリーに対する調査（HEAD = `61dc290d`）。行番号は変更後のファイルのもの。

## 1. 結論（先に）

1. **CMD18（複数ブロック読み出し）・DMA・4 ビット幅・24 MHz は、すでに入っている。** 「マルチブロック化」で稼げる分は、`board-v55`/`v60` の GD-ROM 読み出しではもう取れている（マップ済みトラックの場合）。残っているのは次の 4 点。
2. **最大の遅延は SD ではなく完了通知の 100 ms の下限。** DMA の CD_READ は、FIFO が空になっても最低 100 ms は完了を返さない（`ide.rs` `stream_from_sd` の `min_wait_ms`）。転送そのものは 1 リクエスト数 ms なので、小さい読み出しではこれが全体の 9 割以上を占める [コード]。
3. 持続スループットの上限は、**SD 読み出しとホストへの押し込みが直列**になっていること（どちらも CPU が張り付いて待つ）。重ねれば約 5.5 → 8 MB/s（見積もり）。ただし RAM・`cdda_task` との排他・実機検証の面でリスクが大きいので、今回は**実装せず設計だけ**書く（8 章）。
4. SD のバス速度は 24 MHz（デフォルトスピード上限）。High-Speed（CMD6、48 MHz）で SD 側の時間が約半分になる。
5. 今回、**3 つの feature の裏**に実装した（既定ビルドは 1 バイトも変わらない。9 章で確認）：

| feature | 内容 | リスク |
|---|---|---|
| `fast-complete` | DMA CD_READ の完了を、FIFO が減って空になったのを見たら即返す（100 ms の下限を免除） | 中（完了プロトコルは実機で痛い目に遭った箇所） |
| `sd-multiblock` | 連続読み出しを検出し、完了後の空き時間に次の区間を CMD18 で先読み（キャッシュヒットにする） | 低 |
| `sd-highspeed` | 初期化で CMD6 → HSMODE + 48 MHz。実データを読み戻して検証し、失敗したら 24 MHz に戻す | 中（基板の配線が 48 MHz に耐えるか不明） |
| `sd-fast` | 上の 3 つ全部 | |

feature 名の `sd-multiblock` は依頼の例に合わせた名前で、実体は「先読み」。CMD18 自体は既定で使っている。

## 2. 現状の経路（ファイル:行）

### 2.1 GD-ROM の CD_READ（マップ済みトラック。実際の経路）

```
ホストの CD_READ (0x30)                         ide.rs:1671 handle_cd_read
 └ 範囲検査 → stream_from_sd                    ide.rs:1739 → 2383
    ├ stage_sectors_for(): 1 回に何セクタ置けるか   ide.rs:1836
    │    CD_READ_BUF = 14 KB (ide.rs:1799, SRAM1)
    │    2048 バイト/セクタ: 7 セクタ、2352（生）: 5 セクタ
    ├ stage_chunk(): キャッシュ一致なら SD を読まない   ide.rs:2001
    │   └ fill_cd_read_buf_from_sd()                ide.rs:1898
    │       └ fill_cd_read_buf_raw()  ← エクステント表で直接 SD   ide.rs:1858
    │           ├ track.locate_byte() で連続ブロック数を得る（gdi.rs:117 → fat.rs:271）
    │           ├ hsmci::read_blocks_dma(): CMD18 + DMAC ch1 + CMD12   hsmci.rs:891
    │           │    1 回の上限 MAX_BLOCKS_PER_READ = 128 ブロック（hsmci.rs:880）
    │           └ 生セクタなら 2048 バイトを前へ詰め直す（in place）
    ├ FIFO を (深さ − 8 語) まで先詰め → 完了待ちの前に DMARQ を立てる   ide.rs:2445〜
    ├ push_buf_to_fifo(): DMAC ch0 で FPGA の FIFO へ（半語、SMC 経由）  ide.rs:2779
    │    FIFO の空きを見て押し込む。空きが無ければ yield_now() でポーリング
    └ 残りのチャンクを「SD 読み → push」の繰り返し（直列）   ide.rs:2511 付近
 └ 完了待ち: FIFO が空になるまで 1 ms ごとにポーリング。DMA は最低 100 ms   ide.rs:2561〜
```

- PIO 読み出しは `stream_pio_from_sd`（ide.rs:2650）。同じ `stage_chunk` を使い、ブロック（ホストが示す上限、最大 0xFFFE バイト、ただし 1 チャンク以内）ごとに DRQ を立てる。
- **マップされていないトラック**（FAT を引けなかった、エクステント 96 本超 `fat.rs:38`）は `fill_cd_read_buf_from_sd` の後半、`embedded_sdmmc` 経由になる（ide.rs:1930 付近）。この経路は 1 ブロックずつ CMD17（`blockdev.rs:56`。`embedded-sdmmc 0.9` の `File::read` は 1 ブロックずつ `read` を呼ぶ）、しかも**チャンクごとにボリューム・ディレクトリ・ファイルを開き直して先頭から `seek_from_start`** する（FAT のクラスタ鎖をたどる）。桁違いに遅いので、マルチブロック化の対象外（置き換えるなら鎖を自前で引く必要がある。`gdi.rs`/`fat.rs` は別の担当が触っている）。
- 起動時に IP.BIN の先頭 7 セクタをキャッシュしておく（`prefetch_ip_bin`、ide.rs:2371）。BIOS の最初の CD_READ だけはキャッシュヒット。

### 2.2 SD ドライバ（`embassy-atsam3/src/hsmci.rs`、`opengdemu/src/sdcard.rs`）

| 項目 | 現状 | 根拠 |
|---|---|---|
| MCK | 96 MHz（PLLA） | `embassy-atsam3/src/lib.rs:149` のコメント |
| 初期化クロック | 約 400 kHz（CLKDIV=119） | `hsmci.rs:77〜79` |
| 初期化後 | ACMD6 で 4 ビット、`set_clock_hz(24 MHz)` = CLKDIV 1 → 24 MHz | `sdcard.rs:167〜173` |
| High-Speed | **使っていない**（コメントにも「CMD6 はまだ」） | `sdcard.rs:170〜171` |
| 読み出しの種類 | `read_block`（CMD17、ポーリング PIO）、`read_block_dma[_arm/_finish]`（CMD17 + DMAC ch1）、`read_blocks_dma`（CMD18 + DMAC ch1 + CMD12） | `hsmci.rs:616 / 745 / 891` |
| `read_blocks_dma` は同期 | DMAC 完了 → XFRDONE → CMD12 までスピンで待つ。CPU は空かない | `hsmci.rs:947〜984` |
| DMA の設定 | CHKSIZE=4、ワード幅、BTSIZE は 16 ビット | `hsmci.rs:910〜925` |
| RDPROOF/WRPROOF | 有効（FIFO が埋まればクロックを止める） | `hsmci.rs:82` |
| CMD23（ブロック数の先渡し） | 使っていない（CMD12 で止める） | `hsmci.rs:967` |

HSMCI は GD-ROM の読み出し（`handle_cd_read`）以外に、**`cdda_task`（CD-DA の 4 KB リング、`cdda.rs:458`）と BBA ディスクの読み書き（`handle_disk_read` は 28 ブロックごとに CMD18、8 ブロック未満は CMD17。ide.rs:3015・3082）**も使う。排他は「どの読み出しも同期でスピンするので、await をまたいで SD を使う者がいない」という事実だけに頼っている（明示的なロックは無い）。重ね読みを入れるときの最大の制約（8 章）。

### 2.3 RAM

| 領域 | 内容 |
|---|---|
| SRAM1（4E・2E とも `link/*.x` で 16 KB） | `CD_READ_BUF` 14 KB（ide.rs:1799）。**空きは 2 KB** |
| SRAM0（4E は 32 KB、2E は 16 KB） | 静的領域＋スタック（スタックは約 2 KB と gdi.rs のコメントにある） |
| NFC SRAM（2E のみ使用、4,224 バイト） | `cdda::RING`（cdda.rs:59） |

2 本目の 14 KB バッファは**どちらの MCU にも載らない**。半分ずつの 2 面にすると 1 面 7 KB（2048 バイトなら 3 セクタ、生なら 2 セクタ）になり、CMD18 の固定費が増える（8 章）。

## 3. SD コマンド数

マップ済みトラック、1 リクエスト `n` セクタ、1 回の読み込み単位 `S`（2048 バイトなら 7、2352 バイトなら 5）：

| 単位 | 値 |
|---|---|
| CMD18 | `ceil(n / S)` 回（エクステントの境目で +1） |
| CMD12 | CMD18 と同数 |
| 1 セクタあたり | 約 `2 / S` コマンド（2048 バイト: 0.29、2352 バイト: 0.4） |
| 例：572 セクタ（1ST_READ.BIN） | 82 CMD18 + 82 CMD12（2048 バイト）、115 + 115（2352 バイト） |
| 例：16 セクタ | 3 + 3（2048 バイト）、4 + 4（2352 バイト） |

2352 バイトのセクタは 1 チャンク 5 セクタ → `ceil((head + 5 × 2352) / 512)` = 24 ブロック（約 12 KB）を読んで 10 KB を送る。2048 バイトのトラックは 28 ブロック（14 KB）。

マップされていないトラックは 1 セクタあたり約 4〜5 回の CMD17（2048 バイトなら 4 ブロック、2352 なら 5 ブロック）、加えて FAT のクラスタ鎖の読み出し。

## 4. 時間の見積もり（クロックから。実測ではない）

前提と出典：

| 量 | 値 | 根拠・信頼度 |
|---|---|---|
| SD 4 ビット、24 MHz | 1 ブロック 1,042 クロック（データ 1,024 ニブル + CRC 16 + 開始・終了）= 43 µs → **約 11.8 MB/s** | SD の仕様から計算 [一次資料の理解] |
| SD 4 ビット、48 MHz | 約 23 MB/s | 同上 |
| CMD18 のコマンド＋応答 | 約 100 クロック = 4 µs（24 MHz） | 計算 |
| カードのアクセス遅延（CMD18 から最初のデータまで）| **0.1〜1 ms。未計測**。以降 0.4 ms で計算 | 推測。カードで大きく違う |
| CMD12 + R1b ビジー | 数十 µs | 推測 |
| FIFO への押し込み（DMAC、半語、SMC） | 約 16 MB/s（コード注記）。実際はホストの引き取りが律速 | `ide.rs:2779` の注記。ホストの DMA 引き取りも同程度という前提 [推測] |
| FPGA の読み出し FIFO（主デバイス） | 4,096 語 = **8 KB**、副デバイス 1,024 語 | `fpga/amaranth/hw/ide_device.py:15,23`、`ide.rs:2873` |
| embassy のタイマ刻み | 1 kHz | `ide.rs:3186` 付近のコメント |

2048 バイトのトラック、1 チャンク 14 KB（28 ブロック）：

| 構成 | SD（CMD18 〜 CMD12） | 押し込み | 1 チャンク | 持続速度 |
|---|---|---|---|---|
| **今（24 MHz、直列）** | 0.4 + 1.22 + 0.05 = 1.7 ms | 0.9 ms | 2.6 ms | **約 5.5 MB/s** |
| 48 MHz（`sd-highspeed`） | 0.4 + 0.61 + 0.05 = 1.1 ms | 0.9 ms | 2.0 ms | 約 7.2 MB/s（+30%） |
| 重ね読み（24 MHz） | 1.7 ms（押し込みと並行） | — | 1.7 ms | 約 8.4 MB/s（+53%） |
| 48 MHz + 重ね読み | 1.1 ms | — | 1.1 ms | 約 13 MB/s（ホスト律速に近い） |

2352 バイトのトラック（1 チャンク 5 セクタ = 10 KB、24 ブロック）：現状 0.4 + 1.04 + 0.05 + 0.64 = 約 2.1 ms → **約 4.8 MB/s**。

押し込みの間、MCU は FIFO の空きを `yield_now` でポーリングしているだけで、SD は遊んでいる。SD を読んでいる間、FIFO（8 KB = 約 0.5 ms 分）は空になり、ホストの DMA は DMARQ が落ちて待たされる（コードの注記は、これはフロー制御で許容される、としている）。

**参考**：実物の GD-ROM（12x）は 1.8〜2.7 MB/s 程度（外周で最大）[推測。一次資料は未確認]。現状の見積もり 5 MB/s 前後でも、ドライブより速い。つまり持続速度はもう「ドライブ以上」で、体感の差が出るのはリクエスト単位の遅延（次節）。

### リクエスト単位の遅延（持続速度より効く）

| 要因 | 大きさ | 根拠 |
|---|---|---|
| **完了の下限 100 ms** | 100 ms | `ide.rs:2561〜2562`。`host_took_everything` は「最後の push が返った時点で FIFO がすでに空」のときだけ成立する。FIFO は最後の push 直後は（ホスト律速の push では）ほぼ満杯なので、ほとんどの DMA 読み出しで成立せず、`min_wait_ms = 100`。ループは `i >= min_wait_ms && lvl == 0` で抜けるので、**FIFO が 0.5 ms で空になっても 100 ms 待つ** [コード。実機の計測は無い] |
| 完了待ちのタイマ刻み | 平均 0.5 ms（最大 1 ms） | `ide.rs` 2581 行付近の `Timer::after(1 ms)` |
| 最初のチャンクの SD 読み（キャッシュミス） | 約 1.1〜1.7 ms（上の表） | キャッシュは IP.BIN の最初の読み出しにしか効かない（`stage_chunk` の注記） |
| コマンドの受付 | IRQ 駆動（`pioa_wait_irq`）。遅延は小さい | `ide.rs` `ide_task` |

→ 1 回の CD_READ の所要は、いまはほぼ「転送 + 100 ms」。ゲームが小さい読み出しを数百回する場面では、SD の速度を倍にしても出ない差が出る。**実物の GD-ROM はシークだけで数十 ms かかるので、この 100 ms でも動くが、「本家以上」を言うなら最初に取るべき項目。**

## 5. 改善案の順位

| # | 内容 | 見込み | リスク | 状態 |
|---|---|---|---|---|
| 1 | **完了の 100 ms 下限の免除**（FIFO が減って空になったのを見たら即完了） | 1 リクエストあたり最大約 −100 ms | 中。完了のタイミングは実機で何度も壊れた箇所（`ide.rs:2540〜2560` のコメント）。ただし条件は「FIFO が一度でも減るのを見た」ときだけで、ホストが開始していない場合（FIFO が動かない）は従来どおり待つ | **実装**（`fast-complete`） |
| 2 | **SD 読みと FIFO 押し込みの重ね**（非同期 CMD18 + 2 面または環状バッファ） | 持続 +50%（5.5 → 8.4 MB/s 見積もり） | 高（8 章） | 設計のみ |
| 3 | **High-Speed（CMD6、48 MHz）** | SD 側の時間 −35%（0.4 ms の固定遅延は変わらない）、持続 +30%、最初のチャンクの遅延 −0.6 ms | 中。カード・配線次第。失敗時は 24 MHz に戻す | **実装**（`sd-highspeed`） |
| 4 | **連続読み出しの先読み**（完了後に次の区間を CMD18 で） | 連続するリクエストの最初のチャンクの SD 遅延（約 1.1〜1.7 ms）がゼロ | 低（キャッシュの一致は LBA と長さで検査済み。外れれば読み捨て） | **実装**（`sd-multiblock`） |
| 5 | 読み込み単位を大きくする（CMD18/CMD12 の固定費の按分） | 14 → 28 KB で約 −9% | RAM が無い（2 章） | 見送り |
| 6 | CMD12 の代わりに CMD23（ブロック数の先渡し） | チャンクあたり数十 µs（約 2〜3%） | SCR で対応の確認が要る。HSMCI は CMD23 を別コマンドとして送る必要がある | 見送り |
| 7 | マップされないトラックの経路（CMD17 ×4〜5 + 毎回の鎖の読み直し） | 該当するディスクで数倍 | `gdi.rs`/`fat.rs`（別担当）。`MAX_EXTENTS` の拡大か、鎖を自前で引く | 見送り |
| 8 | FIFO を深くする | 重ね読みと組むなら意味あり。SD 1.7 ms 分を吸収するには約 27 KB 必要 | FPGA の RAM が足りない見込み（EP2C5 の内蔵メモリは約 15 KB、8 KB の FIFO で半分以上。AG16K は未確認）[推測] | 見送り |

「SD の 1 ブロックずつの CMD17 を CMD18 に」は、GD-ROM の経路ではすでに済んでいる。残る CMD17 は、(a) マップされないトラックの経路、(b) 8 ブロック未満の BBA ディスク読み出し（`fetch_run` の `MULTI_MIN`、CMD12 の固定費のほうが高くつくため意図的）。

## 6. 実装の中身

### 6.1 `fast-complete`（`mcu/opengdemu/src/ide.rs` `stream_from_sd` の完了待ち）

完了待ちのループで FIFO の最大レベルを覚え、それより下がったら `pulled = true`。`(i >= min_wait_ms && lvl == 0) || (pulled && 0 を2回続けて読んだ)` で抜ける（R73 S1・S2 の修正：最大レベルは `level_after_prime` から始める。SMC が FPGA のカウンタを非同期に読むので 1 回の読みは裂けうる、2 回目は 1 ms 後なのでほぼ確実に直る）。ホストが動かない場合（FIFO のレベルが動かない）は従来どおり下限まで待ち、200 ms で打ち切る。feature なしのコードは元のまま。

注意点：
- タイマ刻み（1 ms）はそのまま。完了は FIFO が空になってから最大 1 ms 遅れる。
- 先頭チャンクだけで FIFO が空になる小さい読み出しでは、従来の `host_took_everything` と同じ挙動。
- 実機で見る点：(a) BIOS が完了を受け取って IP.BIN → 1ST_READ.BIN へ進むこと、(b) `host reset during CD_READ; no completion` が増えないこと（下限を設けた理由はまさにこれ）、(c) 小さい読み出しの完了までの時間（ログの `CD_READ complete`）。

### 6.2 `sd-multiblock`（`ide.rs` `read_ahead`、`common/sdfast/src/readahead.rs`）

- `handle_cd_read` の `stream_from_sd` が返った後（完了とINTRQはもう送出済み）に呼ぶ。
- 判定は `ReadAhead::record(lba, count, first_chunk_max)`：前のリクエストの終端と今回の開始が一致したときだけ、「終端から、直前のリクエストの先頭チャンクと同じ長さ」を返す。シーク（不一致）では何もしない。長さは `stage_sectors_for`（次のトラックなら次のトラックの値）とトラックの残りで切る（`Prefetch::clamped`）。
- 読むのは `fill_cd_read_buf_raw`（CMD18 の経路）だけ。マップされないトラックは、遅い経路を投機で走らせないので対象外。
- 結果は通常のキャッシュ（`CD_READ_BUF_LBA`/`_LEN`）として入る。`stage_chunk` が LBA と長さを検査するので、外れても余計な 1 回の読み出しだけ。
- ホストが既に次のコマンドを書いた（`command_pending`）か、相手のデバイスにコマンドが来ている（`peer().command_pending()`）か、バスリセット中（`reset_seen`）か、CDDA 再生中のときはやらない。さらに `stream_from_sd`/`stream_pio_from_sd` が全セクタをステージして、ホストが全部引き取り、完了を出したときだけ（`STREAM_OK`、R73 S5）。
- `dma-pattern` feature のときは無効（パターンがバッファを上書きするため）。
- 副作用：先読みの CMD18（約 1〜2 ms）の間は `ide_task` が止まるので、ホストが直後に次のコマンドを書くと、受付がそのぶん遅れる。ミスしたときは同じ読み出しを後から行うことになるので、損は先読みが外れたときの 1 回ぶんだけ。
- 実機で見る点：連続読み出しの 2 回目以降に `cache hit` が出ること、`CD_READ` から DMARQ までの時間が縮むこと、外れたときの悪化がないこと。

### 6.3 `sd-highspeed`（`sdcard.rs` `enable_high_speed`、`hsmci.rs` `read_short_block`/`set_high_speed_mode`、`common/sdfast/src/cmd6.rs`）

手順（R73 の指摘で作り直した版）：4 ビット・24 MHz にした直後に、
1. CMD6 の確認モード（`0x00FFFFF1`）で 64 バイトのステータスを読み、対応ビット（ビット 401）が立ち、かつ要求の結果の欄（グループ 1、ビット 379〜376）が 1 であること（`cmd6::hs_selectable`）。CMD6 に対応しないカード（SD 1.0）はここで失敗して 24 MHz のまま。
2. 24 MHz で、カード全体に散らした最大 48 か所から 14 ブロックの窓を読み、**情報量の多いデータ**（ブロックあたりの異なるバイト値が 160 以上のブロックが 12/14 以上）の窓を最大 4 つ選ぶ（`sdfast::verify`）。同じ窓を 2 回読んで同じハッシュになることも要求。**見つからなければ 24 MHz のまま**（ゼロだらけのカードでは配線の不良を検出できないため）。基準はブロックごとの 32 ビットハッシュで持つ（RAM に載せない）。`ide::loader_scratch()` を使う。IDE タスクが動く前。
3. CMD6 の切替モード（`0x80FFFFF1`）。ステータスのグループ 1 の選択が 1 で、ビジーでなければ成功。
4. 2 ms 待ち、`HSMCI_CFG.HSMODE`（ビット 8）を立て、クロックを 50 MHz 以下の最大（MCK 96 MHz なら 48 MHz）に。
5. 4 つの窓を各 48 回、リトライなしの生の読み出し（`read_blocks_dma_raw`）で読み、**全ブロック**を基準のハッシュと比べる（約 1.3 MB）。HSMCI のデータエラーは `hsmci.rs` が累積した SR で見る（M1）。
6. 失敗したら取り消す（`sdcard.rs` `back_out`）：24 MHz にして（HSMODE は残す。カードはまだ HS）、CMD12（エラー無視）、CMD13 で tran になるまで（最大 10 回）、CMD6 でデフォルトスピード（`0x80FFFFF0`）に切り替えてステータスが 0・非ビジー、HSMODE を落とし、CMD6 の「変更なし」（`0x00FFFFFF`）で選択が 0 と答えること、基準の窓を 24 MHz で読み直して一致。**どれか 1 つでも駄目なら** `init` がカードを 400 kHz・1 ビットに戻して**ハイスピードなしで初期化し直す**。
7. 検証に通った後は `hsmci::set_high_speed_clock` で記録し、**実行中の読み出し（`read_block`・`read_blocks_dma`）でデータの CRC エラーが出たら 24 MHz に落として（HSMODE とカードは HS のまま、これは有効な組み合わせ）読み直す**。以後は 24 MHz。ハイスピードでなくても、CRC エラーは 1 回リトライする。
8. **書き込みは 24 MHz**（`write_block`・`write_multi_begin` ～ `end`/`Drop` の間だけクロックを下げ、終わったら戻す）。HSMODE は書き込みの出力エッジも変えるので 48 MHz の書き込みは検証していない。24 MHz で HSMODE が入った書き込みは、カードが HS モードなので正しい組み合わせだが、これも実機では未検証。

追加した HSMCI の関数（`read_short_block`・`set_high_speed_mode`・`restore_identification_mode` など）は既定のビルドからは参照されないのでリンク時に消える。`read_block`・`read_blocks_dma`・書き込みは M1（SR の累積）で変わっており、既定のバイナリも変わる。

注意：
- `sdcard::init` は起動時に 1 回しか呼ばれない（`main.rs:156`）。ホットスワップの再初期化は現状もクロックを 400 kHz に戻さない。入れるときは HSMODE も落とす必要がある。
- 48 MHz は基板（v5.5 / v6.0）の SD 配線の実力が未知。**v6.0 は SAM3U2E 側の配線が未確認**（`docs/research/ag16k-config.md`）。
- CMD6 の応答に UHS-I や電流制限の確認は入れていない（High-Speed の最大電流は 200 mA で、通常の SD で足りる）。
- 実機で見る点：ログの `SD link: High-Speed @ 48000000 Hz, verified` か、失敗理由。`sd-bench` と組むと SD 単体の速度が分かる（`sd-bench` は IDE の起動を 6 秒遅らせるので計測専用）。

### 6.4 ホストテスト

`common/sdfast`（新規、`no_std`、依存なし）：`cargo test` で 22 件（`verify` 5 件と `cmd6` 3 件は R73 の修正で追加）。
- `readahead`：最初のリクエストは先読みしない／連続なら終端から先読み／シークで連続が切れる／隙間・重なりは連続ではない／長さは先頭チャンクで頭打ち／0 セクタ／アドレスのオーバーフロー／リセット／`clamped`
- `cmd6`：引数の符号化、対応ビット 401、選択ビット 379〜376、ビジービット 273、切替の成否、確認モードの結果欄、R1 のカード状態
- `verify`：ブロックの情報量の判定（ゼロ・テキスト・乱数）、ハッシュが 1 ビットの反転・データ線の固定・ワード順の入れ替えを検出

## 7. 実機で測るべきもの（優先順）

1. **完了の 100 ms の実測**：ログの `CD_READ FAD=… ` から `CD_READ complete` までの時間を、既定のビルドと `fast-complete` で。BIOS が通るかどうかが先。
2. **SD 単体**：`sd-bench`（既定ビルドの 24 MHz）、`sd-highspeed` で 48 MHz。CMD18 の 4／8 ブロックの数値は取れる（`sdcard.rs` の `bench_multi`）。**CMD18 から最初のデータまでの遅延**（上の 0.4 ms の仮定）を知りたい：1 ブロックの CMD18 の所要時間 − 転送時間。
3. **持続速度**：`dma-pattern` なしで 572 セクタの 1ST_READ.BIN の読み出しの `CD_READ complete` までの時間（1.1 MB）。見積もりでは直列 24 MHz で約 0.2 秒、完了待ちが別。
4. **先読みの当たり率**：ゲームごとに `cache hit` の数と、外れた先読みの数（ログを足す必要がある。`read_ahead` は黙って動く）。
5. **ホスト側の引き取り速度**：押し込みがホスト律速かどうか。FIFO のレベル推移（`drain:` ログ）から。

## 8. 重ね読み（最優先の残り）の設計メモ

やること：`read_blocks_dma` を「開始（CMD18 発行 + DMAC 起動）」「完了判定」「終了（CMD12 とエラー確認）」に分け、チャンク `k` を FIFO へ押し込んでいる間にチャンク `k+1` を SD から読む。

障害（実装しなかった理由）：
1. **RAM**：`CD_READ_BUF` は 14 KB で空きは 2 KB。2 面にすると 1 面 7 KB（2048 バイトなら 3 セクタ、2352 なら 2 セクタ）に縮み、CMD18 の固定費（約 0.45 ms/チャンク）が倍になる。見積もり：1 面 7 KB（14 ブロック）で、24 MHz の SD は 0.4 + 0.61 + 0.05 = 約 1.06 ms、押し込みは 0.45 ms。重ねても 1.06 ms/7 KB → **約 6.6 MB/s**。重ねない 14 KB の 5.5 MB/s とほぼ同じ。**48 MHz と組み合わせたときだけ**明確に勝つ。環状バッファ（空いた先頭から次の CMD18 を書き込む）なら 14 KB を使い切れるが、生セクタの詰め直し（in place）と相性が悪い。
2. **`cdda_task` との排他**：今は同期のスピンが暗黙の排他になっている（2.2 節）。非同期にすると、`push_buf_to_fifo` の `await` の間に `cdda_task` が `read_blocks_dma` を呼びうる。対策案：開始した読み出しを他の呼び出しが先に「完了させて結果を保存」する（`settle`）仕組みを `hsmci.rs` に入れる。実機で確かめられない。
3. **FIFO のタイミング**：過去に、押し込みのわずかなずれでホストの DMA が途中で終わった（`stream_from_sd` の注記）。重ねると押し込みの間隔が変わる。
4. **ホストの DMA は SD 読みの間に空になる**現在の挙動が、実機でどれだけ問題かは不明（注記は「許容される」）。重ね読みの効果は、ここの計測（7 章 5）次第。

→ 先に `fast-complete`・`sd-highspeed`・`sd-multiblock` を実機で測り、押し込みがホスト律速か SD 律速かを見てから判断するのがよい。

## 9. ビルド結果

すべて警告のみ（既存の未使用警告）でビルド成功。サイズは `llvm-size` の text + data（バイト）、bss は SRAM0 + SRAM1 + NFC の NOLOAD を含む。

| ビルド | text | data | bss | 備考 |
|---|---|---|---|---|
| 4E 既定（`DEFMT_LOG=info`） | 160,084 | 144 | 26,728 | |
| 4E `sd-fast` | 161,456 | 144 | 26,784 | +1,372 / bss +56 |
| 4E `sd-multiblock` のみ | 160,292 | 144 | 26,736 | +208 |
| 4E `sd-highspeed` のみ | 161,252 | 144 | 26,776 | +1,168 |
| 4E `resident,sd-fast` | 159,224 | 396 | 26,784 | |
| 2E（`--features sam3u2e`、`DEFMT_LOG=off`）既定 | 118,820 | 156 | 26,728 | |
| 2E `sd-fast` | 121,048 | 156 | 26,784 | **+2,228**（128 KB の 2E フラッシュに対し、text+data で 121,204） |
| v60（`--no-default-features --features board-v60`、off）既定 | 65,256 | 156 | 26,728 | AG16K のビットストリームは未配置 |
| v60 `sd-fast` | 67,464 | 156 | 26,784 | +2,208 |
| v60 `resident,sd-fast` | 65,276 | 184 | 26,784 | |

- 4E の ELF は defmt のログ有り（`info`）なので、2E・v60（`off`）より大きい。
- 2E の 121 KB には Cyclone II のビットストリームが入っている（v5.5 の基板に 2E を載せた構成）。v60 の実機のイメージは、AG16K のビットストリームが決まってから +2.2 KB を足して再確認すること（`resident` では 2E のアプリ領域は 120 KB = 122,880 バイト）。
- RAM：feature で増える静的領域は **56 バイト**（`READ_AHEAD` の状態など）。バッファは増やしていない（CD_READ_BUF は 14 KB のまま）。
- **既定ビルドが変わっていないことの確認**：HEAD（`9dfa6ce2`）のワークツリーと、そこへ今回の変更を載せたものを、feature なしで同じ設定でビルドして `llvm-objcopy -O binary` の出力を比較した。2E（`off`）と v60（`off`）は **SHA-256 が一致（バイト単位で同一）**。4E（`DEFMT_LOG=info`）は同じサイズで 51 バイトだけ違う。defmt のログ ID（文字列の位置に依存する）が入れ替わっただけで、コードの差ではない。
- ホストテスト：`common/sdfast` で `cargo test` 14 件成功。

CI（`.github/workflows/build.yaml` の `host-tests`）の matrix には `common/sdfast` が入っている（77 行目、後のコミットで追加済み。この節の最初の版は「まだ足していない」と書いていたが、古い）。
