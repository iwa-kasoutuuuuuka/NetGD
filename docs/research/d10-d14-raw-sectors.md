# D10・D14：純正が 2048 バイト以外で返すセクタ（調べた結果と実装の見積もり）

純正 GDEMU 6.0 の記録（`probe-records/stock_*`）で残っている差のうち、**セクタの長さ**が違う 2 件の中身を、
`tools/mksdcard` の生成コードでバイト単位まで再現した。NetGD のファームはどちらも未対応（常に 1 セクタ 2,048 バイト）。
実装は読み出し経路（DMA・PIO・キャッシュ・先読み）の全体に及ぶので、ここでは中身と変更点の見積もりだけをまとめる。

## 1. 純正が返すバイト列（確認済み）

### D10：CD_READ のバイト 1 = `0x10` で 2,352 バイト

| イメージ | 純正の 2,352 バイト | 確認 |
|---|---|---|
| GDI（2,352 バイトで格納した Mode 1 のトラック） | 格納されたセクタそのまま（同期 12 B・BCD の MSF・モード 1・データ 2,048 B・EDC・0 が 8 B・P/Q の ECC） | 03・08 の `0x10` の CRC が一致 |
| CDI（2,336 バイトで格納した Mode 2 Form 1 のトラック） | 同期 12 B + BCD の MSF（LBA + 150）3 B + `02` + 格納された 2,336 B（サブヘッダ・データ・EDC・ECC） | dcload-ip・04・05・50 の `0x10` の CRC が一致 |

根拠：`python tools/gdprobe/compare.py --manifest <カードの NETGD-PROBE-MANIFEST.json> <記録>` は `0x10` の行も
`mksdcard.sector_for`（`raw_mode1` / `raw_xa_form1`）で再計算して照合する。記録 04・05 で不一致 0（2026-11-22 に再実行：
04 は 1,056 件一致、05 は 2,098 件一致）。

**分かっていないこと**：2,048 バイトで格納した GDI のトラック（`.iso` 形式）に `0x10` を送ったとき、純正が EDC・ECC を作って
返すのか、断るのか。試験用カードのトラックはすべて 2,352 B（GDI）か 2,336 B（CDI）なので、記録が無い。
音声トラックへの `0x10`、`0x10` 以外のデータ選択（ヘッダだけ、サブヘッダだけなど）も未確認。

### D14：CDI の postgap（Form 2 のセクタ）を `0x20` で読むと 2,324 バイト

CDI のデータトラックの後ろの postgap 2 セクタは Mode 2 **Form 2**（サブヘッダの submode = `0x20`。mkdcdisc の `write_mode2_pregap`）。
純正はここを `0x20`（種別を問わない）で読むと **2,324 バイト**を返す。中身は格納された 2,336 バイトの `[8:2332]`
（サブヘッダ 8 B の後ろから、末尾の 4 B（Form 2 の EDC）の手前まで）。

| 候補 | 長さ | CRC-32 |
|---|---|---|
| `FORM2_GAP[8:2332]` | 2,324 | **d0912a98**（純正の記録 05 の `HASH fad=15853 ssz=2324` と一致） |
| `FORM2_GAP[8:2336]` | 2,328 | fcd77903 |
| `FORM2_GAP[0:2324]` | 2,324 | 9111a2a1 |
| NetGD が返す `FORM2_GAP[8:8+2048]` | 2,048 | f1e8ba9e |

つまり純正はセクタごとにサブヘッダの Form ビットを見て、返す長さを変えている。複数セクタの読みで Form 1 と Form 2 が混ざったときの
並べ方（詰めるのか）は未確認（記録の読みは 1 セクタ）。

## 2. 実際の影響

- D10：ゲームがデータトラックを生セクタで読むことはまれ。CD-DA を CD_READ で読むソフトや、生セクタを使うリッパー・診断ソフトが対象。
- D14：postgap はファイルシステムから参照されないので、通常のソフトは読まない。gdprobe のシーク試験がたまたま当たっただけ。

どちらも「今動いているものが動かなくなる」差ではない（NetGD は読めるものを 2,048 B で返している）。

## 3. 実装に要る変更（見積もり）

ファーム（`mcu/netgd/src/ide.rs`）の読み出しは「1 セクタ = 2,048 バイト」を前提に書かれている。2,352 / 2,324 を返すには次の全部に手が入る。

| 場所 | 今の前提 | 要る変更 |
|---|---|---|
| `handle_cd_read` | `SECTOR_BYTES = 2048`、`total = count × 2048` | 要求の出力長（2,048 / 2,352）を決めて下に渡す。D14 はセクタごとに長さが変わる |
| `fill_cd_read_buf_from_sd` / `fill_cd_read_buf_raw` | 格納セクタから `[16..]`（2,352）・`[8..]`（2,336）の 2,048 B を切り出して詰める | 出力長に応じて切り出し方を変える。CDI の生セクタは 16 B の頭を作って足す |
| `CD_READ_BUF`（14 KB）とプリフェッチ | 7 セクタ × 2,048 B（IP.BIN の先読み） | 2,352 B では 6 セクタ。キャッシュの一致判定に出力長を含める |
| `stream_from_sd`（DMA）・`stream_pio_from_sd`（PIO） | チャンクの位置を `× 2048` で計算 | 出力長で計算。DMA の転送長・PIO の DRQ ごとのバイト数（ホストのバイト数上限）も |
| `read_ahead`（`sd-multiblock`） | 2,048 B の並び | 出力長が違う要求では使わない（無効化）のが安全 |
| `fill_pattern`（`dma-pattern`） | 2,048 B | 試験用。同じ式で直す |

- 2,352 B で格納した GDI は格納したまま送るだけ。CDI は 16 B の頭（同期 + MSF + `02`）を作る。どちらも EDC・ECC の計算は要らない。
  2,048 B で格納したトラックへの `0x10` は、純正の動きが分かるまで今のまま（2,048 B）か ILLEGAL REQUEST にする。
- フラッシュ：2E の `release-z`・`resident,sd-fast` は残り約 4.7 KB（R134）。この変更は数百バイトの見込みだが、DMA・PIO の両経路に入る。
- **実機での確認が必須**：転送長が 2,048 の倍数でなくなる（2,352 は 16 ビット単位の倍数だが、FPGA の FIFO と DMA の区切り、ホストの PIO バイト数上限との関係が変わる）。
  完了のタイミングは実機で壊れた前歴がある（R72）。ホストの予測（`expect.rs`）とテストだけで既定のビルドに入れるのは避け、
  feature（例 `raw-sectors`、既定オフ）で入れて実機の gdprobe（`label=netgd`）で純正の記録と比べてから既定にする、が妥当。

## 4. 予測ツール側

`common/discimg/examples/expect.rs` の `CDREAD_FLAGS` は `0x10` でも 2,048 B と予測している（D10 は NetGD 未対応のため）。
ファームに入れるときは、`mksdcard` の `raw_mode1` / `raw_xa_form1` と同じ組み立てを `discimg` の純粋関数にして、ファームと予測の両方から使う
（`--manifest` の照合がそのままテストになる）。
