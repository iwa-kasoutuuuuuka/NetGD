作成日：2026-11-20 / 担当：Fable（設計のみ。コードは変更していない）
対象：`docs/PLAN.md` の G1-1〜G1-4。前提資料は `docs/boards/gdemu60/README.md`、`docs/research/gdemu6-and-parity.md`、

信頼度の表記：**[測定]** = このPCで実行して得た数字。**[一次]** = ソース・データシート・リポジトリ内のファイルを直接読んだ。
**[二次]** = 販売店・ブログ・検索要約。**[推測]** = 上から導いたもの。**[不明]** = 実機か Supra が無いと決まらない。

## 0. 要約

1. **G1 の進め方は、FPGA を誰がコンフィグしているかで決まる。** 作業 2（導通確認）の結果で 4 つに分かれる（§1-3）。
   今回の調査で、刻印どおり末尾に `M` が無い `AG16KDDF256` は「FPGA + DDR の積層品で、内蔵フラッシュは無い」可能性が出てきた [二次]。
   その場合、基板に外付けフラッシュが無い以上、**MCU がパッシブシリアル（PS）で流し込む方式（分岐 A）しか残らない** [推測]。
2. **論理規模は余裕で入る。** Yosys での見積もりは LUT4 2,811 個・FF 1,041 個・メモリ 5 個（102,912 bit）[測定]。
   AG16K（16,624 LE / 504 Kbit）の 17〜23 %。**ただし FIFO のメモリがブロック RAM に推論されなければ 114,153 LUT + 約 104,000 FF になり、7 倍あふれる** [測定]。
   メモリ推論の確保が、FPGA 側の最初の技術課題。
3. **128 KB フラッシュへの同居は「入るかどうか微妙」。** 2E のコードは 64,052 B、ビットストリームに使えるのは 67,020 B [測定]。
   AG16K の非圧縮ビットストリームは 552,366 B [一次]。NetGD の設計を LZMA にかけた大きさは 55〜75 KB と見ている [推測]。
   **Supra で実際に 1 回ビルドすれば基板なしで確定する**ので、そこまで結論を保留する。
4. **最大のリスクは BGA のピン配置。** 169 本の I/O のどれが SMC・G1・水晶につながるかが不明。
   「ピン探索用ビットストリーム」（§2-4）で自動的に洗い出す方法を提案する。
5. **純正に戻す手段は無い。** NetGD を書くには MCU の ERASE が要り、純正ファームは読み出せない。
   純正の FPGA ビットストリームはレジスタ配置が不明で NetGD から使えない。**2 枚目の基板を用意してから ERASE に進むことを勧める。**

### 1-3 判断の分岐（作業 2 の結果で決める）

作業 2（`docs/research/user-tasks.html`）で見るのは、MCU の PA23 / PA24 / PA25 / PB1 / PB2（v5.5 での DATA0 / DCLK / nCONFIG / CONF_DONE / nSTATUS）が
FPGA の方向へ配線されているかどうか。

```
PA23/24/25・PB1/2 から配線が出て FPGA の下に入るか？
├─ はい（5 本とも、または DATA0/DCLK/nCONFIG の 3 本以上）
│    └─ 分岐 A：MCU が PS で流し込む。cyclone.rs の方式を流用する。       ← 本命
├─ 別の MCU ピン 5 本前後が FPGA のコンフィグ用ボールに行っている
│    └─ 分岐 A'：方式は A と同じ。ピンだけ board-v60 で差し替える。
├─ いいえ（MCU から FPGA のコンフィグ線へは何も行かない）
│    ├─ FPGA の JTAG がヘッダ（8 ピンが候補）に出ている
│    │    └─ 分岐 B1：FPGA は内蔵フラッシュから自分で起動。PC + JTAG ケーブルで
│    │              内蔵フラッシュを NetGD のビットストリームに書き換える（1 回）。
│    └─ JTAG もどこにも出ていない
│         └─ 分岐 B2：行き止まり。BGA の下から JTAG を引き出す改造が要る。G1 は保留。
└─ 判別できない（ビアが FPGA の下に潜って追えない）
     └─ 分岐 C：ERASE の前にできる追加確認（§1-5）で A か B を決める。
```

各分岐の内容：

| 分岐 | FPGA の起動 | NetGD がやること | MCU フラッシュの中身 | FPGA の更新 |
|------|-------------|------------------|----------------------|-------------|
| **A** | 電源投入のたびに MCU が PS で流す | `cyclone.rs` を AG16K 向けに直す（§4-3）。ビットストリームは埋め込みか SD（§3） | コード + ビットストリーム（入れば） | ファーム更新（`0xF9`）と一緒に更新できる。SWD は最初の 1 回だけ |
| **A'** | 同上 | 同上 + ピン差し替え | 同上 | 同上 |
| **B1** | FPGA が内蔵フラッシュから自分で読む（AS） | PS ローダは使わない。起動時に「FPGA が期待した版か」を確かめるだけ | コードのみ（64 KB。余裕ができる） | PC と JTAG ケーブルが毎回必要。MCU から書けるのは、AS 用の線が MCU に来ているときだけ |
| **B2** | 同上 | 進めない | — | — |

補足：

- **分岐 A と B は両立しうる。** MSEL1 が AS 側に固定されていても、JTAG からの SRAM 書き込み（`_SRAM.prg`）は常に使える [二次]。
  逆に MSEL1 が PS 側なら、内蔵フラッシュがあっても使われていない。MSEL の符号が Cyclone IV E と同じなら、
  MSEL[2:0] = `000` が PS、`010` が AS なので、**MSEL1 = Low なら PS、High なら AS** になる [推測。Cyclone IV E の表からの類推]。
- **B1 で MCU から内蔵フラッシュを書く案**は、AS 用の 4 線（DCLK / nCSO / ASDO / DATA0）と nCONFIG が MCU に来ている場合にだけ成り立つ。
  その配線があるなら、基板の設計者は PS ではなく「MCU がフラッシュを書き換える」方式を選んだことになる。導通確認で 5 本の行き先が
  「PS の 5 本」か「AS の 4 本 + nCONFIG」かを見分けるのは、ボール名が分からない段階では難しい。JTAG で IDCODE を読める状態になってから決める。
- **内蔵 Cortex コア経由**（Cortex が内蔵フラッシュに書く）は採らない。使うには Cortex 用のファームを別に作って最初に書き込む必要があり、
  その書き込み自体が JTAG を要するので、手間が増えるだけになる。

### 1-4 純正の FPGA ビットストリームを残す案は成り立たない

「FPGA は純正のまま、MCU だけ NetGD にする」ことはできない。理由：

1. **レジスタ配置が違う。** NetGD のファームは SMC の NCS3（`0x6300_0000`）にある自前のレジスタ配置を前提にしている
   （`fpga/amaranth/hw/ide_device.py`、`docs/AddressMapMCU.md`）。純正 FPGA の配置は不明で、一致する理由が無い。
2. **調べる手段が無い。** 純正 MCU ファームは読み出せない前提で（ロックされていれば SWD で読めない）、MCU 側から配置を知ることはできない。
   ビットストリーム側から調べるには、JTAG でフラッシュを吸い出し（B1 のときだけ可能）、AGM の形式を展開し（`rodinia` が対応するのは
   AG16KSDE176 の非圧縮だけ）、ネットリストを復元して意味を読み解く必要がある。G1 の作業量を大きく超える。
3. **分岐 A では、そもそも FPGA にビットストリームが残っていない。** 純正のビットストリームは純正 MCU ファームの中にあり、ERASE で一緒に消える。

結果として起きること：

- **NetGD を書いた基板は、純正の状態に戻せない**（分岐 A でも B でも）。分岐 B1 なら FPGA のフラッシュは JTAG で吸い出して保存できるが、
  MCU の純正ファームが戻せないので、FPGA だけ戻しても動かない。
- **それでも B1 では、書き換える前に必ず吸い出す。** 費用がかからず、後で純正の挙動を調べる唯一の材料になる。

### 1-5 ERASE の前にできる確認（純正を消さない）

作業 2・3 に加えて、次を行うと分岐が確定する。どれも読み取りだけで、純正ファームに影響しない。

| 確認 | 方法 | 分かること |
|------|------|------------|
| 8 ピンヘッダと MCU の導通 | 作業 2 の続き。8 本とも MCU のどのピンにもつながらない（GND・3.3 V を除く）なら FPGA 用の可能性が高い | FPGA の JTAG / AS ヘッダの有無 |
| FPGA 直下のビア | 裏面で、U2 の真下に並ぶビア（1.0 mm 格子の間に出る）と MCU の PA23/24/25・PB1/2 の導通を当たる | 分岐 A の直接の証拠。あわせて §2-4 の方法 1 の準備になる |
| FPGA の IDCODE | 8 ピンヘッダが JTAG らしければ、USB-Blaster 互換ケーブルと Supra（または OpenOCD）で IDCODE を読む | JTAG が生きているか。B1 が可能か |
| コンフィグ用フラッシュの吸い出し | Supra の「Read configuration flash to file」[二次] | 内蔵フラッシュの有無と中身。中身が `ff55…967e3c5a` で始まれば AS 起動で確定 |
| CONF_DONE / nSTATUS の波形 | Dreamcast に挿して電源投入、MCU の PB1 / PB2 と PA24 をロジアナかオシロで見る | PA24 にクロックの束が出て、その後 PB1 が High になれば分岐 A で確定。流している時間も分かる（§3-4 の基準値） |

最後の「波形を見る」は、**分岐 A を最も安く確定できる方法**。純正が実際に何秒かけて流しているか、圧縮ビットストリームかどうか
（ビット数で分かる）、ビット順まで読み取れる。ロジアナがあれば PA23・PA24 の 2 本を記録しておくと、U4（PS の作法）がほぼ全部埋まる。
記録したビット列は純正のビットストリームそのものなので、`docs/research/probe-records/` には置かず、手元だけで扱う。

## 2. ツールチェーン

### 2-1 全体の流れ

```
fpga/amaranth/main.py ──► out/OpenGDEMUCore.v          （変更なし）
                              │
fpga/src/OpenGDEMU.v（上位ラッパ）│  PLL とメモリだけ AG16K 用に差し替え
                              ▼
        Supra 付属 Yosys：synth_agm -top OpenGDEMU -vqm OpenGDEMU.vqm
                              ▼
        Supra af（TCL）：load_architect → read_design_and_pack → read_sdc
                         → place_and_route_design → bitgen normal -prg … -bin …
                              ▼
        OpenGDEMU.bin（PS / フラッシュ用） + _SRAM.prg（JTAG でお試し） + _master.prg（B1 用）
```

Amaranth から Verilog を出すところまでは今と同じ。その先を `fpga/Quartus/` と並べて `fpga/agm/` に新設する。

```
fpga/agm/
  synth.sh / synth.ps1     Supra の場所を環境変数 SUPRA_DIR で受ける
  af_run.tcl               デバイス名・上位モジュール名・入出力ファイル
  OpenGDEMU.asf            ピン配置と I/O 属性（Quartus の .qsf と同じ書式の割り当て）
  OpenGDEMU.sdc            タイミング制約
  ip/audio_pll_agm.v       Audio_PLL と同じ名前・同じポートで中身が AGM の PLL
  ip/fifo_mem_agm.v        （必要なら）M9K を明示的に呼ぶメモリ
  alta-bb.v                Supra 付属のブラックボックス定義（再配布の可否を確認してから置く）
  output/OpenGDEMU.bin     生成物。v5.5 の .rbf と同じくリポジトリに置く
```

`rodinia` の例（`examples/blinky10k/synth.sh`、`af_run.tcl`）がこの流れの実例で、AG10KSDE176 で動いている [一次]。
**AG16K で同じ流れが通ることは未確認**（`rodinia` で AG16K を通しているのは nextpnr 側の実験だけ）。

代替の流れ：Supra には Quartus で合成したネットリストを取り込む方式もある [二次]。その場合 Quartus 側の対象は Cyclone IV E
（EP4CE15F17 相当）になる。手元のコンテナの Quartus 13.0.1 は Cyclone IV E を扱えるはずだが未確認。
**メモリの推論を Quartus に任せられる**のが利点で、§2-3 の問題が Supra 付属 Yosys で解けないときの予備にする。

### 2-2 書き直すもの

| 対象 | 現状（v5.5） | AG16K での扱い |
|------|--------------|----------------|
| `core_pll` | `altpll`、48 MHz × 5。**出力 `c0` も `locked` もどこにも使われていない**（コアは `CLK_48_MHz` を直接使う。Yosys も不要なセルとして消した [測定]） | **移植しない。** AG16K 用のラッパからは外す。v5.5 側から外すかどうかは別件（.rbf が変わる） |
| `Audio_PLL` | `altpll`、11.2896 MHz × 3 = 33.8688 MHz（CDCLK） | AGM の PLL で作り直す。ポート名（`inclk0` / `c0`）を保てば `OpenGDEMU.v` は無変更で済む |
| メモリ（FIFO 5 個） | Quartus が M4K に推論 | §2-3。推論されなければ明示的に M9K を呼ぶ |
| トライステート | `assign X = en ? d : 'bz`（`MCU_DATA`・`DC_DATA`・`DC_INTRQ`・`DC_DMARQ`・`DC_IORDY`、計 35 bit） | そのまま。`synth_agm` が上位ポートの入出力バッファにするはず [推測]。通らなければ `alta_io` 相当を明示する |
| 立ち下がりエッジのレジスタ | `always @(negedge CLK_48_MHz)` × 2 | そのまま |
| ピン配置 | `.qsf` の `set_location_assignment PIN_n` | `.asf` にボール名で書く（§2-4） |
| I/O 規格 | 全ピン `3.3-V LVTTL` | 同じ。AG16K は 3.3 V LVTTL / LVCMOS に対応 [一次]。バンクごとの VCCIO が 3.3 V かは基板で確認 |
| タイミング制約 | `OpenGDEMU.sdc` | §2-5 |

**PLL について分かっていること：**

- `rodinia` の例にあるのは AG1K 用の `alta_pllx`（6 bit の分周パラメータ）[一次]。
  Supra の `alta-bb.v` には `alta_pll` / `alta_pllx` / `alta_pllv` / `alta_pllve` の 4 種がある [一次]。
  **AG16K がどれを使うかは未確認。** データシートが書く「M / N / C カウンタ 1〜512」[一次] は 6 bit の `alta_pllx` と合わないので、
  AG16K は `alta_pllv` か `alta_pllve` の可能性が高い [推測]。
- 決め方：Supra の `generate_pll`（`af -B -X "… generate_pll {Audio_PLL} -pll_type {…} -input_freq {11.2896} -output_freqs {{33.8688}} …"`）で
  AG16K 向けに生成し、出てきた Verilog を `ip/audio_pll_agm.v` として保存する。
- 出力はグローバルクロックに載せる。`rodinia` の例では `cycloneive_clkctrl` で受けている [一次]。
- **PLL の入力は、同じ辺の専用クロックピンからしか入れられない** [一次]。11.2896 MHz が専用クロック入力のボールに来ているかは基板次第。
  純正も 33.8688 MHz を作っているはずなので来ていると見るが、ピン配置が分かるまで [不明]。
- 3 逓倍は PLL 無しでは作れない（48 MHz からは 441/625 倍が必要で、整数比が大きすぎる）。**PLL は必須。**
  「Quartus が PLL を最適化で消し、AGM の配置配線が見つけられない」という報告がある [二次] ので、最初のビルドで PLL が残っているかを確かめる。

### 2-3 メモリの推論（今回見つかった課題）

Amaranth が出す FIFO のメモリは 5 個で、**すべて読み出しが非同期**になっている [一次]：

```verilog
always @(posedge clk) begin
  if (w_port__en) storage[w_port__addr] <= w_port__data;
end
assign r_data = storage[r_port__addr];     // 非同期読み出し
```

| メモリ | 大きさ | bit | M9K の目安 |
|--------|--------|-----|-----------|
| `dev0.read_fifo` | 4096 × 16 | 65,536 | 8 |
| `dev1.read_fifo` | 1024 × 16 | 16,384 | 2 |
| `cdda.fifo` | 768 × 16 | 12,288 | 2 |
| `dev1.write_fifo` | 512 × 16 | 8,192 | 1 |
| `dev0.write_fifo` | 32 × 16 | 512 | 1（FF 512 個でも可） |
| 合計 | | **102,912** | **14 / 56** |

M9K（AG16K も Cyclone IV も）は入力レジスタ付きの同期メモリで、非同期読み出しはできない [一次]。
v5.5 で動いているのは、読み出しアドレスがレジスタなので、Quartus が「アドレスレジスタの入力側をメモリのアドレスレジスタに入れる」形に
自動で組み替えているから（`OpenGDEMU.sdc` のコメント「M4K address register -> RAM -> output mux -> pad」がその結果）。

**オープンな Yosys 0.71 の `synth_intel -family cycloneive` は、この組み替えをしなかった** [測定]。
5 個とも「Bram port A1.1 has incompatible clock type」でブロック RAM に載らず、FF に展開されて
**LUT 97,839 + FF 103,924**（汎用の `synth -lut 4` では LUT 114,153）になった。AG16K の 6〜7 倍。
Supra 付属の Yosys（2019 年ごろの版）の `synth_agm` が同じ結果になるかは [不明] だが、楽観する理由は無い。

対策（上から順に試す）：

1. **そのまま `synth_agm` に通して、M9K（`alta_bram9k`）が 14 個前後できるかを見る。** できれば対策不要。
2. **AG16K 用のメモリを明示する。** Amaranth 0.5 の `amaranth.lib.memory.Memory` は、プラットフォームに `get_memory()` があれば
   そちらに実装を任せる。`main.py` に「AG16K 用の出力」を足し、読み出しを同期（アドレスレジスタの入力を渡す + 書き込みと同時のときは新しい値を返す）
   にしたメモリを返す。**v5.5 用の出力（`out/OpenGDEMUCore.v`）は 1 バイトも変えない**ことを条件にする。
3. **FIFO を同期読み出しに書き直す。** DMA の読み出し経路（`ide_device.py`）のタイミングに触るので、`test_timing.py`・`test_top.py` を通したうえで
   v5.5 の実機でも確認が要る。最後の手段。
4. 予備：Quartus で合成して Supra に渡す流れ（§2-1 の代替）。

どの対策でも、**「メモリを除いた FF が 2,000 個未満」という検査を CI に入れる**（§2-6）。推論が外れたら FF が 10 万個になるので一目で分かる。

### 2-4 ピン配置をどう見つけるか

必要な割り当ては、上位ラッパのポート 25 本・66 bit（`MCU_*` 30、`DC_*` 34、クロック 2）。

**前提として必要な資料：** AG16KDDF256 のボール表（ボール名 ↔ 機能・バンク・専用クロック入力・コンフィグ・JTAG・内蔵 DDR に取られたボール）。
AGM のサイトにあるとされる `AG16KF256_Pinout.xls` と、DDF256 のユーザーマニュアルを入手して `docs/boards/gdemu60/` に置く。
EP4CE15F17 とピン互換という触れ込み [二次] が正しければ、コンフィグと JTAG のボールは次のとおりになる
（**Cyclone IV E の 256 ボール品についての記憶に基づく。ピン表で必ず確かめる**）：
nSTATUS = F4、DCLK = H1、DATA0 = H2、nCONFIG = H5、nCE = J3、CONF_DONE = H14、MSEL0/1/2 = H13 / H12 / G12、TDI = H4、TCK = H3、TMS = J5、TDO = J4。

方法は 4 つ。1 → 2 → 3 の順に使い、4 は検証用。

**方法 1：裏面のビアを当たる（テスター）。**
基板が 2 層か、貫通ビアを使う 4 層なら、BGA の内側のボールは隣のビアを通って裏面に出ている。ビアが緑色の膜で覆われていなければ、
テスターの針が当たる。ボール表を裏から見た向き（左右反転）で印刷して重ね、MCU の各ピン・G1 コネクタの各ピンとの導通を記録する。
ビアは 4 つのボールの間に出るので、1 本のビアにつき候補が最大 4 つ残る。電源・GND・コンフィグ用のボールを除けば、多くは 1〜2 個に絞れる。
外周 2 列のボールは表面の配線で出ていることが多く、写真（`top.jpg`）で追える。
→ **コンフィグ線（分岐の判定）と、クロック 2 本（専用入力ボールは数が少ない）はこの方法で決める。**
SMC と G1 の約 60 本を全部これでやるのは、時間がかかるうえに候補が残る。

**方法 2：ピン探索用ビットストリーム（提案。未検証）。**
自前のビットストリームを 1 回でも流せるようになったら（分岐 A の PS、または JTAG の `_SRAM.prg`）、FPGA 自身にボール名を名乗らせる。

- 設計：全ユーザー I/O を既定で入力（ハイインピーダンス）にする。内部のリングオシレータ（LUT の輪。外部クロックのボールが分からなくても動く）で
  カウンタを回し、**1 本ずつ順番に**出力に切り替えて、そのボールの通し番号を自己同期の符号（パルス幅の比で 0/1 を表す。発振周波数が不正確でも読める）で送る。
  1 本あたり約 50 ms、169 本で 10 秒弱を繰り返す。
- 受け側：MCU 側は SMC・IRQ・クロック出力のピンを全部 GPIO の入力（プルアップ）にした専用ファーム（`board-v60` + `pinfind` feature）で、
  どのピンにどの番号が来たかを RTT に出す。G1 コネクタ側は、基板を Dreamcast から外してロジアナを当てる（電源は別に 3.3 V を与える）。
- 衝突の扱い：同時に出力するのは 1 本だけで、駆動電流は最小に設定する。相手側で出力になっているのは 74HC04 の出力（水晶のバッファ）くらいで、
  そのボールは方法 1 で先に特定して探索対象から外す。内蔵 DDR につながるボールと、専用入力（クロック・コンフィグ）は最初から外す。
- 入力専用のクロックボール：2 回目のビットストリームで、候補のクロック入力（8 本前後）それぞれの周波数を数え、1 回目で判明した MCU 向けのボールから報告させる。
  48 MHz と 11.2896 MHz がどのボールに来ているかが分かる。
- 利点：ボール表さえあれば、ビアを 1 本ずつ当たらなくても SMC の約 30 本が数十秒で決まる。結果は機械的に `.asf` に変換できる。
- **実装（2026-11-22、基板・Supra なしで作れるところまで。実機・ビットストリームは未）**：`fpga/pinfind/README_ja.md`。
  上の案からの変更点：クロック源は AGM の内蔵オシレータ `alta_osc` を第一候補にし、リングと「ボールをクロックに使う」（DCLK を MCU が振る）を予備にした。
  クロックボールの周波数は 2 回目のビットストリームではなく、同じフレームに載せる（クロックプローブ）。出力はオープンドレインが既定で、出す前に聞いて Low なら飛ばす。

**方法 3：JTAG のバウンダリスキャン。**
FPGA の JTAG が出ていれば、`SAMPLE` 命令で全ボールの状態を読める。MCU 側のピンを 1 本ずつ GPIO で動かしながら読めば対応が取れる。
設計を書き込まなくても使えるのが利点（純正のビットストリームのままで調べられる）。
ただしスキャンセルとボールの対応表（BSDL）が要る。AGM が配布しているかは [不明]。EP4CE15F17 の BSDL が流用できるかも [不明]。
BSDL が手に入るなら方法 2 より先に試す価値がある。

**方法 4（検証）：仮のピン配置で作った本番ビットストリームを流し、MCU から FPGA[12] が `0xC0DE` と読めるかを見る。**
読めれば SMC のアドレス・データ・ストローブがすべて正しい。1 本でも違えば読めないので、最終確認として強い。
G1 側は `fpga-diag` のカウンタ（ストローブ数・RSTn のエッジ数）と `tools/gdprobe` で確かめる。

### 2-5 I/O 属性とタイミング制約

**I/O 属性**

| 項目 | 方針 |
|------|------|
| 規格 | 全ピン 3.3 V LVTTL（v5.5 と同じ） |
| 未使用ボール | **入力・ハイインピーダンス**に固定する。何につながっているか分からないボールを出力にしない |
| 内蔵 DDR | 使わない。DDR を休止させておくのに必要な信号（CKE を Low、CS# を High など）を、ユーザーマニュアルのピン名で確認して出す [不明] |
| コンフィグ中のピン状態 | Cyclone IV は弱いプルアップ付きの入力になる。AG16K が同じかは [不明]。Dreamcast のバス（INTRQ / DMARQ / IORDY）への影響があるので、最初の実機確認で測る |
| 駆動能力 | `DC_DATA` は G1 バスを駆動する。v5.5 の既定値（Cyclone II の 3.3 V LVTTL 既定）に近い値から始め、波形を見て決める |

**タイミング制約**（`fpga/Quartus/OpenGDEMU.sdc` から移す内容）

| 制約 | 内容 | 注意 |
|------|------|------|
| `create_clock` | `CLK_48_MHz` 20.833 ns、`CLK_11_2896_MHz` 88.577 ns | そのまま |
| PLL の出力クロック | `derive_pll_clocks` | Supra の `read_sdc` が対応するか [不明]。無ければ `create_generated_clock -multiply_by 3` を手で書く |
| クロック間 | 48 MHz 系と 11.2896 MHz 系は非同期（`set_clock_groups -asynchronous`） | 対応していなければ `set_false_path` を双方向に書く |
| SMC 読み出し | ポート間の組み合わせ経路 60 ns（`set_max_delay`） | ポートからポートへの `set_max_delay` を Supra が解釈するか [不明] |
| G1 出力 | クロックから `DC_DATA` などへ 20 ns | v5.5 で「16 ns が限界、12 ns は不可」だった経路。**AG16K の実力は別物なので、最初のビルドの報告で見直す** |
| G1 入力・SMC 書き込み | 入力から 48 MHz まで 20 ns | 同上 |
| CDDA | 11.2896 MHz から SCK / SDAT / LRCK へ 15 ns | 同上 |

`rodinia` の例にある `.sdc` は `create_clock` だけの単純なもの [一次]。Supra がどこまで解釈するかは、実際に読ませて警告を見るしかない。
解釈されない制約は「黙って無視」になりうるので、**配置配線後の報告（`setup.rpt` など）に該当経路が載っているかを毎回確かめる**。

### 2-6 CI への影響

- **Supra は CI に載せない。** AGM が配る実行ファイルで、再配布の条件が確認できていない（公開リポジトリのコンテナに入れられない）。
  ライセンスサーバやドングルが要るという情報は見つかっていないが、条件の文面も見つかっていない [不明]。
- **ビットストリームは手元でビルドして、生成物をコミットする。** v5.5 の `fpga/Quartus/output_files/OpenGDEMU.rbf` と同じ扱い。
  コミットのたびに、Supra の版、入力の `OpenGDEMUCore.v` の SHA-256、生成物の SHA-256 を `fpga/agm/output/BUILD.txt` に残す。
- **CI に足せるもの（オープンなツールだけで動く）：**
  1. 今ある「Amaranth → Verilog が再現する」検査はそのまま。
  2. **YoWASP 版 Yosys（`pip install yowasp-yosys`）による構造検査**：上位ラッパごと読み、メモリを残したまま LUT4 に落として、
     「メモリが 5 個」「FF が 2,000 個未満」「LUT が 6,000 個未満」を確かめる。§2-3 の退行と、規模の急増を捕まえる。約 2 分。
  3. ファームの `board-v60` ビルド（生成済みの `.bin` を使う）と、フラッシュ使用量の上限検査（リンクが通ること自体が検査になる）。
- 自前のランナー（Supra を入れた PC）で夜間ビルドする手もあるが、G1 が実機で動いてから考える。

### 3-1 いまの 2E の使用量 [測定]

2026-11-20、`mcu/netgd` で `DEFMT_LOG=off cargo build --release --features sam3u2e` を実行し、`llvm-size -A` で読んだ値
（他の作業と並行中の作業ツリーでの値。コミットごとに数百バイト動く）。

| 領域 | 大きさ（B） | 備考 |
|------|------------:|------|
| `.vector_table` | 184 | |
| `.text` | 61,804 | 更新プログラム（`fwupdater`）の埋め込みを含む |
| `.rodata` | 1,948 | |
| `.data`（初期値） | 116 | |
| **コード小計** | **64,052** | |

### 3-2 ビットストリームの大きさ

| 対象 | 大きさ（B） | 根拠 |
|------|------------:|------|
| Cyclone II EP2C5、非圧縮 | 158,224 | [一次] `build.rs` |
| 同、Quartus 圧縮（`.rbf`） | 73,821 | [測定] |
| 同、さらに LZMA（辞書 4 KiB、lc=lp=pb=0） | 49,632 | [測定] |
| **AG16K、非圧縮（`.bin`）** | **552,366** | [一次] `rodinia` の `blinky16k.bin` |
| 同、ほぼ空の設計を LZMA（同じ設定） | 10,403 | [測定] `blinky16k.bin` を `xz` にかけた。**下限** |
| 同、AGM の圧縮（LZW）をかけた大きさ | 不明 | [不明] Supra で出すしかない |
| **同、NetGD の設計を LZMA** | **55〜75 KB** | [推測] 下の根拠 |

推測の根拠：Cyclone II では、非圧縮 158,224 B を LZMA にかけると約 44.6 KB になる（`build.rs` の「約 5 KB 小さい」から）。
これが NetGD の設計の「情報量」にあたる。AG16K に同じ論理を載せると、使う LUT と配線の数はほぼ同じで、
1 か所あたりの位置を表すのに要るビットが少し増える（デバイスが 3.5 倍広いため）。ここに空の設計の下限 10.4 KB を足して 55〜75 KB と見た。
**上限の 67,020 B をまたいでいる**ので、入るとも入らないとも言えない。

→ **Supra が手に入ったら、ピン配置は仮のままで 1 回ビルドして `.bin` を作り、次の 2 つを測る。基板は要らない。**

```
xz --format=raw --lzma1=preset=9e,dict=4KiB,lc=0,lp=0,pb=0 -c OpenGDEMU.bin | wc -c        # 非圧縮 → LZMA
xz --format=raw --lzma1=preset=9e,dict=4KiB,lc=0,lp=0,pb=0 -c OpenGDEMU_compressed.bin | wc -c   # AGM 圧縮 → LZMA
```

### 3-3 選択肢

| 案 | 内容 | 利点 | 欠点 | 使える分岐 |
|----|------|------|------|-----------|
| **E 埋め込み** | 今と同じ。LZMA で `.flash1` に置き、展開しながら PS で流す | 仕組みが今のまま。SD が無くても FPGA が起動する。ファーム更新と FPGA 更新が 1 つのファイル | 入らないかもしれない。入ってもコードを増やす余地が減る | A / A' |
| **S SD から読む** | SD のルートに `NETGD.BIT`（仮）を置き、起動時に読んで流す | フラッシュの制約が消える。FPGA だけの更新が SD のコピーで済む | **SD が無いと FPGA が起動しない。** 起動が遅くなる（§3-4）。ファームと FPGA の版がずれうる | A / A' |
| **F 内蔵フラッシュに 1 回書く** | JTAG で AG16K のコンフィグ用フラッシュに書く | 電源投入と同時に FPGA が自分で起動する（MCU を待たない）。MCU のフラッシュが空く | 内蔵フラッシュがあり、JTAG が出ていて、MSEL1 が AS 側のときだけ。更新のたびに PC と JTAG ケーブルが要る | B1 |
| **H 併用** | 埋め込みを既定にし、SD に `NETGD.BIT` があればそちらを優先 | 開発中に FPGA だけ差し替えられる | 流す前に SD を初期化するので、SD があるときは S と同じだけ遅い | A / A' |

### 3-4 「FPGA をできるだけ早く起こす」制約との関係

`main.rs` の `main_task` は「FPGA を最初に起こす。それより前に何も足さない」という作りになっている。
基板の電源は Dreamcast から来るので、FPGA が起きるまで Dreamcast は応答しない GD-ROM バスと、止まった CDCLK を見ることになる。

**今の所要時間は記録が無い**（`info!("FPGA Loaded! ({} ms)")` は出ているが、数字を残した資料がリポジトリに見当たらない）。
以下は構造から出した目安で、実測ではない。

| 段階 | v5.5（今） | AG16K・案 E | AG16K・案 S |
|------|-----------|-------------|-------------|
| 流すビット数 | 590,568（73,821 B） | 非圧縮なら **4,418,928**（今の 7.5 倍）。AGM 圧縮なら大きさに比例 | 同左 |
| PS で流す時間 | 1 bit あたり NOP 20 個 + GPIO 3 回。仮に 1〜2 Mbit/s なら 0.3〜0.6 秒 | 非圧縮を同じ速度で流すと **2.2〜4.4 秒** | 同左 |
| LZMA の展開 | 流す処理と交互に進む | 同じ（出力が 7.5 倍なので展開も長い） | 不要（生で置く） |
| SD の初期化 | FPGA の後 | FPGA の後 | **FPGA の前**。カードの応答待ち（ACMD41）が規格上最大 1 秒、普通は 0.05〜0.5 秒 |
| FAT を開いてファイルを探す | — | — | 数十 ms |
| ファイルの読み出し | — | — | 552 KB。1 MB/s でも 0.55 秒（流す処理と交互） |
| 追加の待ち合計 | — | **+2〜4 秒**（非圧縮の場合） | **+2.5〜5.5 秒** |

読み取れること：

1. **案 E と S の差（SD の初期化で +0.1〜1.5 秒）より、ビット数が 7.5 倍になる影響（+2〜4 秒）のほうが大きい。**
   つまり、先に手を打つべきは「流す時間」のほう。
2. **AGM の圧縮ビットストリームを使えば、流すビット数が減る。** `build.rs` が Cyclone II で「Quartus の圧縮を切らない」理由と同じ。
   フラッシュ上の大きさは LZMA 単独より少し増えるが、起動時間のほうが優先。どちらにするかは §3-2 の 2 つの数字と、流す時間の実測で決める。
3. **ビットバンを速くする余地がある。** `cyclone.rs` の `delay()` は NOP 5 個 × 4 回。AG16K の DCLK の上限が分かれば削れる。
   もう一歩進めるなら、DATA0 / DCLK のピンが MCU のシリアル周辺機能（USART の同期モードや SPI）に割り当てられるかを調べ、ハードウェアに送らせる。
   6.0 のピンが v5.5 と同じ PA23 / PA24 なら、SAM3U のピン機能表で確認する（未確認）。
4. **Dreamcast がどこまで待てるかは測っていない** [不明]。実物のドライブはディスクの回転が上がるまで数秒かかるが、
   その間もバスには応答している。「バスが無応答」の許容時間は別の話で、G1-4 で「FPGA が起きるまでの ms」と「起動できたか」を対にして記録する。
   §1-5 の波形観測で、**純正が何秒かけているか**が分かれば、それが実績のある上限になる。
5. **案 F（B1）なら、この問題は起きない。** FPGA は MCU と無関係に、電源投入から自分で読む。

### 3-5 推奨

- **分岐 A / A'：まず案 E を試す。** Supra で出した実際の大きさが 67,020 B − 余裕 8 KB（約 59 KB）以下なら E で決まり。
  超えるなら H（埋め込みは無し、SD 必須）ではなく、次の順で考える：
  (1) コードを削る（`fwupdater` の埋め込み、使っていない応答テーブル、`list_root_dir` の起動時ログなど）、
  (2) 辞書を大きくして圧縮率を上げる（今は作業 RAM の都合で 4 KiB。`CD_READ_BUF` の 14 KB を借りているので 8 KiB までは入る見込み）、
  (3) それでも入らなければ案 S。そのときは「SD が無い・ファイルが無い」ときの LED 表示を決める。
- **分岐 B1：案 F。** MCU 側は「FPGA の版を読み、期待と違えば LED で知らせて止まる」だけにする。
- どの案でも、**FPGA にビットストリームの版を返すレジスタを足す**（今の `0xC0DE` の隣。Amaranth 側の小変更）。
  ファームと FPGA が別々に更新されうる案 S・F では必須、案 E でも取り違えの発見に役立つ。

## 4. ファームのボード分岐

### 4-1 feature の形

```toml
# mcu/netgd/Cargo.toml
[features]
default   = ["board-v55"]
board-v55 = []                 # SAM3U4E + Cyclone II（v5.5 / v5.15b クローン）
board-v60 = ["sam3u2e"]        # SAM3U2E + AG16K（GDEMU 6.0 クローン）
```

## 5. リスクと段階的な計画

### 5-1 リスク

| # | リスク | 影響 | 起こりやすさ | 手当て |
|---|--------|------|--------------|--------|
| R1 | **BGA のピン配置が分からない** | ビットストリームが作れない。G1 が止まる | 高 | §2-4。ボール表の入手を最優先にする。ピン探索用ビットストリームを先に用意する |
| R2 | **コンフィグ方式が B2（JTAG も PS も届かない）** | G1 は改造なしでは不可能 | 低〜中（U2 の調査で B の見込みは下がった） | §1-5 の確認を ERASE の前に済ませる |
| R3 | **Supra が手に入らない／`AG16KDDF256` を選べない／配置配線が通らない** | ビットストリームが作れない | 中 | 入手は Windows 版・Linux 版の両方を試す。デバイス名が無ければ `AG16KF256` で作り、DDR 用のボールを避けて配置できるかを見る。`rodinia` の例（AG10K）を先に通して手順を確かめる |
| R4 | **FIFO がブロック RAM に推論されない** | LUT 114,153 + FF 約 104,000 で 7 倍あふれる [測定] | 中 | §2-3 の対策 1〜4。CI に FF 数の検査 |

| R11 | 6.0 に UART が無く、`DEFMT_LOG=off` でログも無い | 立ち上げ時に何が起きているか見えない | 中 | 立ち上げ中だけ RTT を使う（ログ入りは 128 KB に入らないので、ビットストリームを埋め込まない `fpga-from-sd` か、ローダだけの小さな診断ファームで）。LED の点滅コードを決める |
| R12 | Supra 付属 Yosys が古く、Amaranth の出す Verilog を読めない | 合成が通らない | 低 | 通らなければ、オープンな Yosys で一度 `write_verilog -noattr` に通して平易な Verilog に落としてから渡す |

### 5-3 規模の見積もり（今回実施）[測定]

**方法：** `fpga/amaranth/out/OpenGDEMUCore.v` と `fpga/src/OpenGDEMU.v` を、PLL だけブラックボックスにして Yosys 0.71
（YoWASP 版。`pip install --target <作業用フォルダ> yowasp-yosys` で、リポジトリの venv には入れていない）に読ませた。
リポジトリの venv にある `amaranth-yosys` は Amaranth の出力専用に削った版で、`read_verilog`・`techmap`・`abc`・`stat` が無いため使えなかった
（`python -m amaranth_yosys -p help` で確認）。

メモリをセルのまま残して LUT4 に落とすスクリプト：

```
read_verilog bb.v OpenGDEMUCore.v OpenGDEMU.v
hierarchy -top OpenGDEMU; proc; flatten; tribuf
opt -full; wreduce; peepopt; opt_clean; alumacc; share; opt; fsm; opt -fast
memory -nomap; opt_clean
opt -fast -full; techmap; opt -fast; abc -lut 4; opt -fast; clean
stat
```

**結果：**

| 資源 | NetGD の設計 | AG16K の容量 | 使用率 | 参考：EP2C5（v5.5） |
|------|-------------:|-------------:|-------:|--------------------:|
| LUT4 | 2,811 | — | — | — |
| FF | 1,041 | — | — | — |
| LE（LUT と FF が同居できる分だけ減る） | **2,811〜3,852** | 16,624 | **17〜23 %** | 4,608 に対し 61〜84 % |
| メモリ | 5 個・102,912 bit（M9K 約 14 個） | 504 Kbit（M9K 56 個） | 20 %（個数で 25 %） | M4K 26 個・119,808 bit に対し 86 % |
| PLL | 1（`Audio_PLL`。`core_pll` は未使用で消えた） | 4 | 25 % | 2 |
| トライステート | 35 bit | — | — | — |
| I/O | 66 bit | 最大 169 | 39 % | — |

読み方と限界：

- **桁の確認であって、Supra の結果ではない。** 加算器を桁上げ線を使わずに LUT で組んでいるので、LUT 数は実際よりやや多めに出る。
  一方、メモリを同期読み出しに直すための回路（§2-3）は含んでいない（数十 LE の見込み）。
- EP2C5 で 61〜84 % という値は、v5.5 で実際に収まっている事実と矛盾しない。見積もりの妥当性の裏づけになる。
- **メモリをブロック RAM に載せない場合**（`synth -lut 4` をそのまま実行）は LUT 114,153・FF 約 103,900。
  `synth_intel -family cycloneive` でも LUT 97,839・FF 103,924 で、5 個とも M9K に載らなかった（§2-3）。
- 動作周波数は見積もっていない（オープンなツールに AG16K の遅延情報が無い）。Supra での 1-d で出す。

結論：**容量は問題にならない。AG16K は NetGD の設計の 4〜6 倍の余裕がある。** 課題は容量ではなく、メモリの推論・ピン配置・コンフィグ経路。

## 6. ユーザーへの確認事項

優先度の高い順。

1. **基板をもう 1 枚用意できますか。** ERASE の後は純正に戻せません。1 枚しか無い場合、作業 1（純正のプローブ記録）を取り切ってから進めます。
2. **U2 の刻印の末尾に `M` はありますか**（`AG16KDDF256` か `AG16KDDF256M` か）。内蔵フラッシュと内蔵マイコンの有無の手がかりです。
3. **作業 2 に次を足せますか。**
   (a) 8 ピンヘッダの各ピンが MCU のどこにもつながらないか（GND・3.3 V を除く）。
   (b) 裏面の U2 直下にビアが並んでいるか、テスターの針が当たるか（緑の膜で覆われていないか）。裏面の U2 直下を真上から撮った写真があると助かります。
   (c) SD スロットのカード検出・ライトプロテクトの接点が MCU のどのピンに行くか。
4. **ロジアナかオシロスコープはありますか。** あれば、電源投入時の PA23 / PA24 / PB1 / PB2（MCU の 103 / 105 / 55 / 57 番ピン）を記録すると、
   コンフィグ方式・所要時間・ビット順が一度に分かります（純正を消さずにできます）。ピン探索の G1 側の記録にも使います。
5. **USB-Blaster 互換の JTAG ケーブルを用意できますか**（数百円〜）。8 ピンヘッダが FPGA の JTAG だった場合、IDCODE の読み出し、
   フラッシュの吸い出し、`_SRAM.prg` でのお試し書き込みに使います。分岐 A でも、切り分けの手段として有用です。
6. **Supra を入れる PC はどれにしますか。** Windows 版と Linux 版があります。AGM のサイトか販売店からの入手になり、登録が要るかもしれません。
   このPC に入れてよければ、入手できた時点で §5-2 の 1-c・1-d をこちらで実行します。
7. **AG16KDDF256 のユーザーマニュアルとボール表（`AG16KF256_Pinout.xls` など）を入手できますか。** 公開の場所が見つからない場合、
   販売店（海振遠など）への問い合わせが必要になります。こちらでも探します。
8. **FPGA 用の 48 MHz は、v5.5 ではどのピンから出ていますか。** `docs/PCB.md` は PA28（PWMH0）、ファームは PCK0 を PA21 に出しています。
   上流の記述のずれなので、v5.5 の基板をお持ちでなければ、6.0 でのクロック探索（§2-4）の結果で決めます。
9. **SD カードが無いと起動しない構成（案 S）は許容できますか。** ビットストリームが 128 KB に入らなかった場合の話です。
   本家は SD 無しでも電源が入ります（公式ページ）。
