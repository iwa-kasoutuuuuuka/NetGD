# 設計：自己更新の安全対策 B ― ロックした常駐ブート領域

2026-11-20、Fable。**設計のみ。実装・実機確認は一切していない。** 対象は `docs/research/LOG.md` R37 の対策 B。
前提は R37（レビュー）、R46（対策 A、OGFW 形式 2）、R49 と `docs/research/ag16k-config.md`（AG16K のコンフィグ）、
`docs/design/g1-ag16k-port.md` §3（2E のフラッシュ予算、ビットストリームを SD から読む案）。

根拠の印：**[一次]** SAM3U データシート（Atmel-6430G、節番号を併記）／**[測定]** 今回 `llvm-size`・`llvm-nm` で読んだ値／
**[推測]** 構造からの見積もりで、実測していないもの／**[不明]**。

---

## 0. 要約

1. **R37 の素描どおりの B（ビットストリームごとロックし、復旧は `0xF9` だけ）は勧めない。** 理由は 3 つ。
   (a) 電源を入れ直した後、Dreamcast は送信プログラム（`netgd-fwupd`）を読み込めない。dcload のディスクを出しているのは NetGD 自身だからである。
   `0xF9` だけに答える「更新モード」は、送り手がまだ RAM に残っている間（＝対策 A で既に救えている場面）にしか役に立たない。
   (b) 2E + Cyclone II では、今のコード量だと空きが約 2 KB しか残らない（R37 の「約 12 KB」はコードが 4.8 KB 小さかった時点の値）。
   (c) ビットストリームを更新するたびに SWD かロック解除が要る。
2. **勧める形（B-SD）：常駐領域はロック領域 1 個（8 KB）だけ。復旧は SD カードから。**
   常駐部は「クロック → アプリの長さ・CRC・ベクタを検査 → ジャンプ」と、「SD のルートの `NETGD.OGF` を読んでアプリ領域に書く」だけを持つ。
   FPGA・Dreamcast・LAN が無くても復旧できる。ビットストリームは今と同じくアプリのイメージの中（4E はプレーン 1）で、ロックしない。
   試作の実測で **4,308 バイト**（§5）。8 KB に 3.5 KB ほど余る。
3. フラッシュの代償は 2E で **8 KB ちょうど**。アプリ側は「リンク位置をずらす・記述子を置く」だけで、ローダーも更新プログラムも今のまま。
4. 代償：FPGA の起動が、アプリの CRC 検査のぶん **約 20〜55 ms 遅れる** [推測]。これを避けたいなら常駐部に FPGA ローダーを持たせる形（16 KB、§2-4 の I-A）になる。
5. B の後に残る「SWD でしか戻せない」場面は、**常駐部そのものの書き換え**と**常駐部のバグ**、**GPNVM の誤操作**だけになる（§4）。
   GPNVM0（セキュリティビット）を立てるコマンド語 `0x5A00000B` は、今の「ページ 0 を EWP する」語 `0x5A000003` と 1 ビット違い。
   B ではページ 0 への EWP 自体が無くなるので、この近さも消える（§3-4）。

## 1. フラッシュの配置

### 1-1 SAM3U のフラッシュの性質 [一次]

| 項目 | SAM3U2E | SAM3U4E | 出典 |
|------|---------|---------|------|
| フラッシュ | 128 KB、1 プレーン（0x00080000〜） | 128 KB × 2（0x00080000〜、0x00100000〜） | §8.2.3.1、`link/*.x` |
| EEFC | 1 個 | 2 個（EEFC0・EEFC1） | §8.2.3.3 |
| ページ | 256 バイト | 256 バイト | 表 8-3 |
| ロック領域 | **8 KB（32 ページ）× 16 個** | 8 KB × 16 個 × 2 プレーン | 表 8-3 |
| GPNVM | 2 ビット（0 = セキュリティ、1 = 起動元） | 3 ビット（2 = プレーンの入れ替え）。EEFC0 だけが持つ | §8.2.3.10 |

- ロックされた領域への書き込み・消去は**中止され、プレーン全体に影響しない**。`EEFC_FSR` の FLOCKE が立つ（§20.4.2）。
- 「全消去」コマンド EA は、ロックされた領域が 1 つでもあると拒否される（§20.4.3.3）。
- SLB / CLB / GLB / GPNVM 系のコマンドの間は**フラッシュを読める**（§20.4.3.4・§20.4.3.5 の注）。EWP の間は読めない（だから書き込み部は RAM で動かす）。
- ロックは**ソフトから CLB で外せる**。つまりロックは「悪意」ではなく「バグと事故」への備えである。
- ERASE ピン（200 ms 以上 High）：フラッシュ全体、**全ロックビット**、GPNVM1 を消す（§8.2.3.4、§8.2.4）。GPNVM1 が 0 になるので、次の起動は ROM（SAM-BA）。

### 1-2 配置の基本形（B-SD、推奨）

常駐部はロック領域 0（8 KB）。アプリ領域はその直後から。アプリのイメージは「ベクタ → 記述子 → コード → ビットストリーム → CRC」の 1 本。

```
SAM3U2E（128 KB）
0x00080000 ┬ 常駐部（ロック領域 0、8,192 B、ロック）      使用 約 4.6 KB
0x00082000 ┼ アプリ領域（122,880 B、ロックなし）
           │  +0x000  ベクタテーブル（184 B）
           │  +0x100  記述子 "NGAP"（32 B、§2-5）
           │  +0x120  .text / .rodata / .data の初期値
           │  …       .flash1（LZMA のビットストリーム。SD から読む構成では無し）
           │  末尾 4 B CRC32（イメージの先頭からここの直前まで）
0x000A0000 ┴

SAM3U4E（128 KB × 2）
0x00080000 ┬ 常駐部（EEFC0 のロック領域 0、8 KB、ロック）
0x00082000 ┼ アプリ領域（122,880 B）：ベクタ、記述子、コード、CRC
0x000A0000 ┴
0x00100000 ┬ ビットストリーム領域（プレーン 1、131,072 B、ロックなし）
           │  LZMA のビットストリーム ＋ 末尾 CRC32。記述子が番地と長さを指す
0x00120000 ┴
```

### 1-3 場合ごとの空き

2E のコード量は、今の作業ツリーのビルド（`DEFMT_LOG=off --features sam3u2e`、15:11 の ELF）の値 [測定]：
`.vector_table` 184 + `.text` 65,176 + `.rodata` 3,320 + `.data` 156 = **68,836 B**。`.flash1` 49,632 B。合計 118,468 / 131,072、**空き 12,604 B**。
（`g1-ag16k-port.md` §3-1 の時点は 64,052 B。同じ日のうちに 4.8 KB 増えている。）

アプリのイメージ = コード 68,836 + 記述子と詰め物 104 + CRC 4 = **68,944 B** として計算した。

**SAM3U2E**

| ビットストリーム | 置き場所 | B-SD（常駐 8 KB、推奨） | I-A（常駐 16 KB、FPGA ローダーも常駐） | R37 の素描（ビットストリームもロック） |
|------------------|----------|------------------------|----------------------------------------|----------------------------------------|
| Cyclone II、49.6 KB | 埋め込み | 空き **約 4.1 KB**（3 %） | 空き 約 1.6 KB [推測] | ロック 64 KB、アプリ領域 64 KB、空き 約 2 KB [推測] |
| AG16K 小、40 KB 以下 | 埋め込み | 空き **約 13.9 KB** 以上 | 空き 約 11.2 KB 以上 [推測] | ロック 48 KB、空き 約 18 KB [推測] |
| AG16K 大、55〜75 KB | **SD の `NETGD.BIT`** | 空き **約 53 KB** | 空き 約 50 KB [推測] | **入らない**（R37 のとおり） |
| 埋め込める上限 | | 53.9 KB（予備 8 KB を残すなら **45.7 KB**） | 51.2 KB（同 43.0 KB）[推測] | — |

- I-A と R37 の素描の「アプリ」は、今のコードから更新プログラムの埋め込み 2,188 B [測定] とローダー・LZMA 約 3.3 KB [推測。試作の差分 3,556 B から] を引いた 約 63.4 KB で計算した。
- **2E + Cyclone II という基板は実在しない**（v5.5 は 4E、6.0 は AG16K）。この行はビルドできる唯一の 2E 構成としての目安。
- 予備 8 KB を残す場合、AG16K を埋め込めるかの境目は、今の「約 54 KB」（131,072 − 68,836 − 8,192）から **約 46 KB** に下がる。

**SAM3U4E**

| ビットストリーム | 置き場所 | プレーン 0 の空き（常駐 8 KB） | プレーン 1 |
|------------------|----------|-------------------------------|-----------|
| Cyclone II、49.6 KB（v5.5） | プレーン 1 | `DEFMT_LOG=info` の既定ビルドでコード 109,944 B [測定、14:40 の ELF] → 空き **約 12.8 KB**。ログなしなら 2E と同程度のコードで 約 54 KB [推測] | 81 KB 空き |
| AG16K 小・大 | プレーン 1 | 同上 | 75 KB でも入る。LZW だけ（LZMA なし）でも 128 KB まで |

4E では 3 つの場合のどれでも埋め込みで足りる。**注意：4E の既定ビルド（ログあり）は、常駐部を 16 KB にすると空きが 約 5 KB まで減る。** 8 KB に収める理由の 1 つ。

### 1-4 ビットストリームを SD から読む場合（AG16K 大）

- ファイル：SD のルートの `NETGD.BIT`（仮）。中身は OGFW 形式 3 の種別 1（§2-6）＝ヘッダ 512 B ＋ ペイロード。CHIPID・版・CRC の検査をそのまま使える。
- **B-SD では読むのはアプリ**（アプリは SD・FAT の実装を全部持っている）。常駐部は関与しない。記述子の `bs_kind` を「SD」にしておく。
- 起動時間への影響（`g1-ag16k-port.md` §3-4 と同じ見積もり）[推測]：SD の初期化が FPGA の前に来て +0.05〜1 秒、ファイルを探すのに数十 ms、
  読み出しは DMA の複数ブロックで 552 KB でも 0.1〜0.3 秒。流す時間（R49：0.5〜3.3 秒）のほうが大きい。
- **カードが無い・ファイルが無い・CRC が合わないとき：FPGA は起きない。** Dreamcast からは GD-ROM のバスが無応答に見える。
  埋め込みなら「カードなし」でも空のドライブとして答えられるが、SD 方式ではそれができない。
  そのとき本体の BIOS がどう振る舞うかは [不明]（実機確認 H7）。LED の点滅で知らせる。カード無しでは元々何もできない機器なので、実用上の差は「メニューに入れるか」だけ。
- FPGA とファームの版がずれうるので、FPGA に版レジスタを足す（`g1-ag16k-port.md` §3-5 と同じ結論）。記述子に「期待する版」を入れて照合する。
- I-A（常駐部が FPGA を起こす形）にした場合は、常駐部の小さい SD リーダー（1 ビット幅、ポーリング、約 1 MB/s [推測]）で読むので、552 KB なら +0.5 秒ほど余計にかかる。

## 2. 常駐部の中身と起動の流れ

### 2-1 まず決めること：復旧の経路

依頼の素描は「アプリが無効なら FPGA を起こし、`0xF9` だけに答える更新モード」だった。これには実用上の穴がある。

- 送り手の `netgd-fwupd` は dcload-ip から起動する（`tools/netgd-fwupd/README_ja.md`）。dcload のディスクイメージを Dreamcast に出しているのは NetGD のアプリである。
- 常駐部の更新モードは `0xF9` にしか答えないので、**電源を入れ直した後の Dreamcast はディスクを読めず、送り手を起動できない。**
  ディスクを 1 枚出せるだけの ATAPI の実装（`ide.rs` の `handle` だけで 12.7 KB [測定]）を常駐部に入れるのは大きさの面で論外。
- 送り手がまだ動いている間（転送の中断、ホストの一時的な不調）は、今の対策 A でも RAM 上の更新プログラムが生きていて再送できる。

つまり「`0xF9` の更新モード」が新しく救えるのは、**別の手段で送り手を起動できる人**（BIOS を dcload に改造した本体など）だけである。

一方、SD カードは MCU の HSMCI に直結していて、FPGA が無くても読める。カードは NetGD の利用者なら必ず持っている。
→ **復旧は「SD のルートに更新ファイルを置いて電源を入れる」にする。** 純正 GDEMU の更新のしかたと同じ発想で、Dreamcast も LAN も要らない。

以下、これを **B-SD** と呼ぶ。`0xF9` の更新モードは「後から足せる追加」として §2-4 の I-A に残す。

### 2-2 常駐部が持つもの（B-SD）

| 部品 | 内容 | 大きさ |
|------|------|-------:|
| ベクタテーブル | 16 語（SP、Reset、例外は全部「LED を点滅して止まる」）。割り込みは使わない | 64 B |
| クロック・ピン | 12 MHz 水晶 → PLLA 96 MHz、FWS、PIO のクロック、LED・ボタン | 約 0.3 KB |
| アプリの検査 | 記述子（マジック・版・記述子の CRC・長さの範囲）、イメージ全体の CRC32、ベクタ（SP は SRAM0 の中、Reset/NMI/HardFault は奇数でアプリ領域の中）。`fwupdater_logic` の関数を共用 | 約 0.5 KB |
| ジャンプ | `VTOR = APP_BASE`、MSP を入れ、Reset へ分岐 | 38 B |
| SD リーダー | HSMCI をポーリングで初期化（CMD0/8/55/41/2/3/7/16）、CMD17 で 1 ブロックずつ。1 ビット幅、DMA なし、読むだけ | 約 0.7 KB |
| FAT32 リーダー | MBR の第 1 パーティション（無ければ先頭が BPB）、ルートから 8.3 名のファイルを 1 つ探し、クラスタ連鎖をたどる。読むだけ。exFAT・FAT16 は非対応 | 約 0.6 KB |
| 更新の本体 | 1 回目：ファイル全体を読んで検査（ヘッダ・CHIPID・宛先・CRC）。2 回目：書く。最後にフラッシュ上の CRC を検査 | 約 0.75 KB |
| フラッシュ書き込み | EWP と GLB だけ。`EEFC_FCR` に書く関数は 1 つで、RAM にコピーして動かす（§3-4） | 約 0.15 KB |
| 自己ロック | 起動時に GLB で確かめ、領域 0 がロックされていなければ SLB（§3-2） | 約 0.1 KB [推測] |
| LED の点滅コード | 失敗の理由を回数で示す | 68 B |
| **合計** | | **約 4.6 KB / 8,192 B** |

個々の値は §5 の試作の `llvm-nm` から。持たないもの：FPGA ローダー、LZMA、ビットストリーム、IDE、`0xF9` の処理、ログ、割り込み、書き込み可能な静的変数。

### 2-3 起動の流れ（B-SD）

```
リセット（0x0 は フラッシュ 0x80000 の写し。GPNVM1 = 1）
 └ 常駐部 Reset
    1. クロックを 96 MHz に、ピンを設定
    2. 領域 0 のロックを確認。外れていれば SLB（開発用ビルドでは省く）
    3. 復旧の要求があるか：
         (a) 前面ボタンが押されたまま（PA20 が Low。20 ms 間隔で 3 回一致）
         (b) GPBR0 に合言葉（アプリが「SD から更新して」と頼んでリセットした）
    4. 要求が無ければアプリを検査：記述子 → CRC → ベクタ
         合格 → VTOR を設定してアプリへ（ここまで 約 20〜55 ms [推測]）
    5. 要求がある、または検査に落ちた → 復旧モード
         WDT を止める → SD を初期化 → NETGD.OGF を探す
           見つかって検査に通る → アプリ領域に書く → フラッシュ上で再検査 → リセット
           カードなし・ファイルなし・検査に落ちた → LED で理由を点滅。
             アプリが有効なら（＝ボタンで入っただけなら）数秒後にアプリを起動、
             無効なら 1 秒おきにカードを見直し続ける（後から挿しても進む）
```

決めごと：

- **ファイルがあるだけでは書かない。** 書くのは「アプリが無効」「ボタン」「アプリからの要求」のどれかのときだけ。
  毎回の起動で SD を初期化しない（起動を遅らせない）、ファイルを消す必要がない（常駐部は SD に書かない）ため。
- **書く前にファイル全体を検査する**（1 回目の読み）。対象の CHIPID、宛先 = `APP_BASE`、長さ、CRC、ベクタ。違う基板用のファイルや壊れたファイルでは 1 ページも消さない。
- **先頭の 2 ページ（ベクタと記述子）は最初に消し、最後に書く。** 途中で電源が落ちたら記述子が無いので、次の起動は CRC を計算するまでもなく復旧モードに入り、同じファイルで何度でもやり直せる。
- 書いている間、FPGA は起きていないので Dreamcast は無応答のバスを見る。復旧は「本体の電源を入れて LED を見る」操作になる。終わったら本体の電源を入れ直す。
- WDT：`WDT_MR` は 1 回しか書けない [一次、§14]。通常の経路では常駐部は触らず、アプリに任せる（リセット後の既定は約 16 秒で、常駐部の通常経路は 0.1 秒未満）。復旧モードに入るときだけ止める。
- ボタンと LED のピンは v5.5 で PA20 / PB18。**6.0 では不明**（`g1-ag16k-port.md` §4-2）。ボタンが無い・分からない基板では (a) を外し、(b) と「アプリが無効」だけで入る。

LED の点滅コード（案）：2 = カードなし／3 = ファイルなし／4 = 読み取りエラー／5 = ヘッダか対象が違う／6 = アプリ領域がロックされている／7 = 書き込みエラー／8 = ファイルの CRC 不一致／9 = 書いた後の検査に失敗／速い点滅 = 書き込み中。

### 2-4 常駐部とアプリの境界：3 つの形

| | **I-B：常駐部は最小（推奨）** | I-A：FPGA の起動も常駐部 | R37 の素描：ビットストリームもロック |
|---|---|---|---|
| 常駐部 | 8 KB（使用 約 4.6 KB） | 16 KB（使用 約 8〜10.7 KB [測定]） | 48〜64 KB |
| FPGA を起こすのは | アプリ（今のまま） | 常駐部。記述子が指すビットストリームを、アプリの CRC より先に流す | 常駐部 |
| 通常の `0xF9` 更新 | アプリが RAM の更新プログラムへ渡す（今のまま） | 更新プログラムを常駐部に置き、アプリが常駐部の入口を呼ぶ（アプリから 2.2 KB 減る） | 同左 |
| 復旧 | SD | SD。FPGA が起きれば `0xF9` の更新モードも足せる | `0xF9` だけ（§2-1 の穴） |
| アプリとの取り決め | 「VTOR を設定して飛ぶ」「記述子」「GPBR0 の合言葉」だけ | 上に加えて「FPGA は設定済み」「常駐部の入口の表」「PS のパラメータを記述子で渡す」 | 同左 |
| 2E での代償 | 8.2 KB | 約 10.9 KB [推測]（16.4 − ローダー 3.3 − 更新プログラム 2.2） | ロックの端数で 5〜7 KB 余計に失う |
| FPGA の起動の遅れ | **CRC のぶん 約 20〜55 ms** [推測] | ほぼ 0 | ほぼ 0 |
| ロックの中で凍るもの | 起動と SD 復旧だけ | **PS ローダーと LZMA も凍る** | ローダー、LZMA、ビットストリーム |

I-B を勧める理由：

1. **常駐部は SWD でしか直せない。だから、まだ固まっていないものを入れない。** AG16K の PS のビット順・CONF_DONE 後のクロック数・タイミングは未確定（R49 の 5・7）。
   I-A ではそれがロックの中に入る。記述子でパラメータを渡せば和らぐが、ローダーの作りそのものの誤りは直せない。
2. アプリの変更が最小（リンク位置と記述子）。ローダー・LZMA・更新プログラム・`fwupdate.rs` はそのまま。
3. 取り決めが少ないほど、古い常駐部と新しいアプリの組み合わせで困らない。
4. 4E の既定ビルド（ログあり）でも収まる（§1-3）。

I-A を選ぶ理由があるとすれば「FPGA の起動を 1 ms も遅らせたくない」こと。今の `main.rs` はそれを最優先にしている。
ただし、いま FPGA を流すのに 0.3〜0.6 秒 [推測。`g1-ag16k-port.md` §3-4。実測の記録なし] かかっており、その 5〜15 % にあたる。
I-B で遅れを縮める手：CRC を 4 ビット表引き（表 64 B）にして 約 18 ms [推測]。それでも気になるなら、記述子に「コードだけの CRC」を持たせ、
ビットストリームの正しさは LZMA の復号エラーと FPGA 自身の CRC（nSTATUS / CONF_DONE）に任せる（コード 69 KB なら 約 10 ms [推測]）。
実機で測ってから決める（H2）。

「アプリが常駐部のローダーを関数として呼ぶ」形（共有ローダー）は採らない。FPGA の読み込みは起動時に 1 回だけで、共有しても得るものが無く、呼び出しの取り決めが凍るだけだから。

### 2-5 アプリを途中の番地にリンクする

- `link/sam3u2e.x`・`sam3u4e.x`：`FLASH : ORIGIN = 0x00082000, LENGTH = 0x0001E000`。
  cortex-m-rt はベクタテーブルを `ORIGIN(FLASH)` に置くので、それだけでベクタが `APP_BASE` に来る。
- 記述子：`_stext = ORIGIN(FLASH) + 0x120;` として `.text` を後ろへ下げ、
  `.app_desc ORIGIN(FLASH) + 0x100 : { KEEP(*(.app_desc)) } > FLASH`（`INSERT AFTER .vector_table`）で 32 B の場所を空ける。
  SAM3U のベクタは 16 + 30 = 46 語 = 184 B なので 0x100 までに収まる。
- VTOR：常駐部が `SCB->VTOR = APP_BASE` を書いてから飛ぶ。`TBLOFF` は 128 B 単位なので `0x82000` は問題ない。
  アプリ側でも起動直後に同じ値を書く（常駐部を信用しすぎない）。cortex-m-rt 0.7.3 には `set-vtor` の機能が無いので、`#[pre_init]` か `main` の先頭で 1 行書く。
- 引き渡すときの状態：割り込みは 1 度も有効にしていない、MSP はアプリのベクタの値、**クロックは 96 MHz のまま**。
  アプリの `PowerManagementController::init` は「既に PLLA で動いていて設定が同じなら何もしない」に直す
  （MCK の元になっている PLLA を書き直すのは危険。作り直すと PLLACOUNT のぶん 約 15 ms [一次の式から計算] 余計にかかる）。
  設定が違うときだけ、MCK をいったんメインクロックに戻してから作り直す。
- 記述子（32 B、リトルエンディアン）：

  | オフセット | 内容 |
  |-----------:|------|
  | 0 | マジック `"NGAP"` |
  | 4 | 記述子の版（1） |
  | 8 | イメージの長さ（末尾の CRC を含む。512 の倍数） |
  | 12 | ビットストリームの番地（絶対番地。2E はイメージの中、4E は `0x00100000`。SD なら 0） |
  | 16 | ビットストリームの長さ（圧縮後） |
  | 20 | ビットストリームの展開後の長さ |
  | 24 | 上位 8 ビット：ビットストリームの種別（0 = なし／SD、1 = LZMA）。残り：アプリの版 |
  | 28 | ここまでの 28 B の CRC32 |

  長さと CRC はリンク後に `fwimage.py` が埋める（ELF の中は 0）。I-B の常駐部が使うのは「長さ」と「記述子の CRC」だけで、ビットストリームの欄はアプリ自身と `fwimage` の検査用。
- **開発時の問題：`probe-rs run` は ELF をそのまま書くので、CRC が入らない。** 対策を 2 つ用意する。
  (1) `fwimage.py seal <elf>`：ELF の該当セクションに長さと CRC を書き込んだ ELF を出す（配布用・CI 用）。
  (2) 開発用の常駐部（feature `dev`）：「長さ 0 の記述子」を未封印として受け入れ、CRC を飛ばす。自己ロックもしない。**配布する常駐部には入れない。**

### 2-6 OGFW 形式 3

形式 2 との違いだけを書く（`tools/fwimage/FORMAT.md` を改訂する）。

| 項目 | 形式 2 | 形式 3 |

- `fwimage.py build`：ELF のロード番地が `APP_BASE` 未満なら拒否。記述子の場所にマジックが無ければ拒否。記述子と末尾 CRC を埋めてからヘッダを作る。

- 送り手（`tools/netgd-fwupd/fwcore.c`）：形式 3 の検査。`tools/fwimage/vectors/*.txt` を形式 3 で作り直し、3 者（Python・Rust・C）で同じベクタを使う今の仕組みを続ける。

## 3. ロックビット

### 3-1 どこをロックするか

- **EEFC0 のロック領域 0 だけ**（I-A なら 0 と 1）。アプリ領域とプレーン 1 はロックしない。
- SLB の引数はページ番号で、その領域の中のどのページでもよい [一次、§20.4.3.4]。領域 0 なら `FARG = 0`。

守りは 2 重にする：(1) 書き込み部が宛先を自分で確かめる（`APP_BASE` より前へは書かない。更新プログラムも常駐部も）、(2) それでも出てしまった EWP を EEFC が止める（ロック）。

### 3-2 いつロックするか

| 案 | 内容 | 評価 |
|----|------|------|
| SWD で書くときに手でロック | OpenOCD なら `flash protect`。probe-rs での手段は [不明] | 道具に依存し、忘れる |
| **常駐部が起動のたびに確かめ、外れていれば自分でロック（推奨）** | GLB → 領域 0 のビットが 0 なら SLB → もう一度 GLB | 道具に依存しない。ERASE して書き直した後も自然に戻る。ロック済みなら読むだけなので NVM を消耗しない |

- SLB / GLB の間はフラッシュを読める [一次] ので RAM で動かす必要は無いが、`EEFC_FCR` に書く場所を 1 つにするため、RAM の同じ関数を使う。
- 開発用（feature `dev`）は自己ロックしない。SWD で何度も書き直すため。
- 常駐部は **CLB を持たない**。ロックを外す手段はファームのどこにも無い。

### 3-3 常駐部そのものの更新

- **SWD だけ。** `0xF9` でも SD でも書けない（宛先の検査で拒否、さらにロックで拒否）。
- ロックした領域を SWD で書き直せるか：probe-rs の ATSAM3U 用フラッシュアルゴリズムが書く前にロックを外すかどうかは [不明]（H4）。
  外さないなら、OpenOCD の `flash protect 0 0 0 off`、または ERASE ピン → GPNVM1 を立て直す → 全部書き直し、の手順を `INSTALL.md` に足す。
- 常駐部の版は、常駐部の末尾の固定番地（`0x00081FF0`）に置き、アプリが読んでログと IDENTIFY の応答に出す。現場で「どの常駐部か」が SWD なしで分かるようにする。

### 3-4 ERASE と GPNVM、とくにセキュリティビット

- ERASE ピン：フラッシュ全体・全ロック・GPNVM1 を消す。常駐部も消える。SWD で常駐部とアプリを書き、GPNVM1 を立てれば元に戻る。**ERASE は常に最後の手段として残る。**
- **GPNVM0（セキュリティビット）が立つと SWD が使えなくなり、ERASE ピンでしか戻せない** [一次、§8.2.3.5]。立てるのは SGPB（コマンド `0x0B`）で引数 0、
  つまり `EEFC_FCR = 0x5A00000B`。**引数 0 は「何も入れなかったとき」の値**なので、SGPB を出すコードがどこかに 1 行あるだけで事故の種になる。
- GPNVM1 を消す（CGPB、引数 1）と次から ROM（SAM-BA）で起動し、フラッシュのファームは動かない。SWD では戻せるが、現場では文鎮と同じ。

コードで不可能にする方法：

1. **`EEFC_FCR` に書く関数は、常駐部に 1 つ、更新プログラムに 1 つだけ。** ほかの場所は番地 `0x400E0804` / `0x400E0A04` を持たない。アプリ（`opengdemu`・`embassy-atsam3`）は今も `FMR` しか書いていない。これを保つ。
2. その関数の引数は列挙型。**許可するコマンドは、更新プログラムが EWP（`0x03`）と GLB（`0x0A`）、常駐部がそれに SLB（`0x08`）を加えた 3 つだけ。**
   SGPB（`0x0B`）、CGPB（`0x0C`）、EA（`0x05`）、CLB（`0x09`）、WPL / EWPL（`0x02` / `0x04`）は型に存在しない。
3. 引数の範囲も同じ関数で確かめる：EWP のページは `APP_BASE` 以降（プレーン 0 ではページ 32 以上）、SLB のページは常駐部の中（0〜31）。
4. コマンド語を作る部分は純粋関数 `fcr_word(cmd, arg) -> Option<u32>` にして、**ホストで総当たり**（コマンド 256 通り × 引数の境界値）で
   「許可した組み合わせ以外は `None`」「結果の下位 8 ビットが `0x0B`・`0x0C`・`0x05`・`0x09` になることは無い」を確かめる。
5. CI で、常駐部と更新プログラムの逆アセンブルに対し「`EEFC_FCR` の番地を作る箇所が 1 つ」を検査する（R46 で更新プログラムを逆アセンブルで確かめたのと同じやり方を自動にする）。
6. ROM の IAP 関数（§22.4.4）は使わない。任意のコマンド語をそのまま実行する入口だから。

今より良くなる点：いまの更新プログラムは、ページ 0 を書くときに `0x5A000003` を出す。**セキュリティビットを立てる語 `0x5A00000B` とはビット 3 が違うだけ。**
B では EWP の引数が必ず 32 以上になるので、この語は出なくなる。なお、引数が GPNVM の本数以上の SGPB は何もしない [一次、§20.4.3.5]。
つまり B の後は、コマンドの 1 ビットが化けて SGPB になっても、引数が 32 以上なので無害である。

## 4. B の後に残るもの、A だけの場合との比較

| 場面 | A だけ（今） | B-SD |
|------|--------------|------|
| `0xF9` の転送中に電源断・本体リセット・LAN 断 | **SWD**（転送の間ずっと、数十秒） | 次の起動で復旧モード。SD の `NETGD.OGF` で戻る。ファイルが無ければ PC でカードに置く |
| ページ 0 を書く数 ms の電源断 | **SWD** | 同上（アプリの先頭ページが無効なだけ。常駐部のベクタには誰も触らない） |
| CRC は合うが起動しない・動かないイメージ | **SWD**（ベクタの形しか見ていない） | ボタンを押しながら電源 → SD から書き直し。**ボタンが無い基板では SWD**（Reset で即座に固まるアプリは GPBR の要求も出せない） |
| 強制リセット（`F9/59`） | **SWD** になりうる | 復旧モードに入るだけ |
| 違う基板用のイメージ | 拒否（A） | 拒否（更新プログラムでも常駐部でも） |
| SD 復旧の途中の電源断 | — | 何度でもやり直せる（先頭 2 ページが最後） |
| ビットストリームの更新に失敗（2E：アプリと一体／4E：プレーン 1） | **SWD**（2E）／FPGA が起きないが MCU は動く（4E。`0xF9` は FPGA が要るので結局 SWD） | アプリごと無効 → SD 復旧（2E）。4E はアプリが FPGA の失敗を見て GPBR で復旧を頼む |
| **常駐部の書き換え** | — | **SWD だけ**（そもそも現場ではやらない） |
| **常駐部のバグ**（SD の初期化がある種のカードで通らない、FAT の読み違い、検査の誤り） | — | **SWD**。小さく保ち、ホストテストと実機の電源断試験で固める以外にない |
| GPNVM の誤操作 | SWD（GPNVM1）／ERASE（GPNVM0）。語が 1 ビット違い | コードに経路が無い（§3-4）。残るのは SWD の操作ミスだけ |
| 常駐部の導入そのもの | — | 最初の 1 回は SWD。SWD なしの移行（§6 の D3）を選ぶなら、その 1 回だけ A と同じ窓 |
| SD スロットの故障、FAT32 でないカード（exFAT） | — | 復旧できない（LED 3 または 2）。別のカードを FAT32 で用意する。`tools/mksdcard` が作る形式なら可 |
| フラッシュの寿命・ハードの故障 | 同じ | 同じ。常駐部は自己ロックの 1 回以外、自分の領域に書かない |

R37 の素描（ビットストリームもロック）を選んだ場合に加わる窓：ビットストリームの更新には SWD か「ロックを外す経路」が要る。
後者を作ると、外して書き直している間は復旧モードの FPGA が無く、`0xF9` の復旧そのものが効かない。B-SD は復旧に FPGA を使わないので、この問題が無い。

### 6-2 オーナーに決めてほしいこと

| # | 決めること | 推奨 | 理由・代償 |
|---|-----------|------|-----------|
| D1 | 復旧の経路：SD／`0xF9` の更新モード／両方 | **SD だけ** | `0xF9` は電源を入れ直すと送り手を起動できない（§2-1）。両方にするなら I-A（16 KB）が前提 |
| D2 | 境界：I-B（8 KB、FPGA が 約 20〜55 ms 遅れる）／I-A（16 KB、遅れなし、ローダーが凍る） | **I-B**。H2 の実測で遅れが問題なら「コードだけの CRC」、それでもだめなら I-A | §2-4 |
| D3 | 既に NetGD が入っている基板への導入：SWD で書く／**SWD なしの移行**（「常駐部＋アプリ」を 1 本の形式 2 のコード画像にして、今の更新プログラムで書く。初回起動で自己ロック） | 開発機は SWD。配布を考えるなら移行画像も用意 | 移行はその 1 回だけ A と同じ窓がある。SWD を持たない人にも B を届けられる |

### 6-3 進めてよい条件・やめる条件

進めてよい：

- 4E（v5.5）：今すぐ。プレーン 0 の空きは既定ビルドで 約 12.8 KB 残る。
- 2E（6.0）：ビットストリームが **約 46 KB 以下なら埋め込み**、それを超えたら **SD の `NETGD.BIT`**（そのとき常駐部の 8 KB は問題にならない）。
  どちらになっても B-SD は成り立つので、**B の可否は Supra の数字を待たなくてよい**。待つのは「埋め込みか SD か」だけ。

やめる・設計を見直す：

- H1：VTOR を移した状態で embassy の割り込み（SysTick、PIOA、HSMCI、DMAC）が正しく動かない。
- H3：ポーリングの SD 初期化が手持ちのカードで安定しない（常駐部のバグは SWD でしか直せないので、ここが固まらないならロックしない）。
- H4：ロックが効かない、またはロックした基板を SWD で書き直す確実な手順が作れない。
- H2：FPGA の起動の遅れで Dreamcast が起動しなくなる（その場合は I-A へ）。
- コードが増えて 2E の空きが 8 KB を割り、しかもビットストリームを SD に出せない事情があるとき。

R37 の素描どおりの形（ビットストリームをロック、`0xF9` で復旧）は、§0 の 3 つの理由で **不採用を勧める**。

### 6-4 S0 レビュー（R59）で加わった条件と実機の確認項目

- **ロックの前に**：FAT リーダーを mksdcard・mkfs.fat・Windows のフォーマットで作ったカードのイメージで試す（32 GB 級の配置、FAT の予約上位4ビット、FAT ミラーのフラグ）。
- **書き込みのコードは RAM 上の1つの関数**（ラッチ書き込み → FCR → FSR のポーリング → FSR を返す、タイムアウト付き）。2E はプレーン0を書きながらプレーン0から命令を読めない。
- **正誤表 46.1.1.3 / 46.2.1.2**：書き込みコマンドの間は FWS = 6。
- FLOCKE・FCMDE は FSR の読み取りで消えるので、FRDY を見た同じ読み取りから取る。ラッチは 32 ビット単位で書く。
- SLB の引数は 0 だけ、GLB には引数 3 以上を入れる（化けてもセキュリティビットにならないように）。GLB に引数を入れても FRR が同じことを実機で確かめる。
- 復旧の要求（GPBR0）は復旧の前に消す。ボタンが押しっぱなし・浮いている場合に書き直しを繰り返さない。
- 4E の GPNVM2、未知の CHIPID、6.0 のボタンのピンの扱いを決める。
- SLB 0（`0x5A000008`）は CLB 0（`0x5A000009`）と1ビット違い。常駐部はロックの後に GLB で読み直し、外れていれば次の起動で再ロックする（R61）。
- ボタンで要求した復旧は、検証の後でカードが壊れると有効な旧アプリを失う（先に頭のページを消すため）。設計どおり。
- 同じイメージ（長さ・トレーラ CRC・4E はビットストリームの CRC が一致）なら書き込まない。ボタンが押しっぱなしでも書き換え回数を消費しない。

## 7. 引き渡しの取り決め（別ファイル）

常駐部からアプリへ飛ぶ瞬間の状態、GPBR、常駐部の版と世代、ロックの手順、アプリがしてはいけないことは
**`docs/design/resident-app-contract.md`** にまとめた（設計のみ、未実装）。そちらが次の箇所を置き換える：

- §2-3 の WDT（「復旧モードに入るときだけ止める」）→ 常駐部は `WDT_MR` を書かず、復旧中は `WDT_CR` で巻き戻す（同 §2-3、オーナーの判断 E1）。
- §2-3 の「書く → 再検査 → リセット」→ R61 のとおり、成功したらリセットせずにアプリへ飛ぶ。どの経路でも飛ぶときの状態は同じ（同 §2）。
- §2-3 のボタンの「3 回一致」→ 1 回目が押されていなければ読み足さない（毎回の起動を 40 ms 遅らせないため）。
- §2-5 の「引き渡すときの状態」→ 同 §2 の表。記述子の版は 1 で凍り、新しい欄は拡張ブロック `"NGAX"` に置く（同 §3-5）。
- §3-3 の「版を 0x00081FF0 に置く」→ 16 バイトの情報ブロック（同 §3-3）。
