# 設計：常駐部とアプリの引き渡しの取り決め（インターフェース世代 1）

2026-11-20、Fable。**設計のみ。コードは変えていない。実機では何も確かめていない。**
親の設計は `docs/design/fw-bootloader.md`（B-SD / I-B、判断 D1〜D7）。ここは、その §2-5「引き渡すときの状態」を、
ロックの前に凍らせる仕様として書き直したもの。発端は LOG の R59（正誤表、GPBR）、R60（WDT、4E のビットストリーム）、R61（SLB/CLB）、R75（2E の残り 1.7 KB）。

根拠の印：**[一次]** SAM3U データシート Atmel-6430G（節番号。行番号はスクラッチパッドの `sam3u.txt`）／**[コード]** リポジトリの `ファイル:行`／
**[推測]** 読解や見積もりで、実測していないもの／**[不明]**。

**改訂（2026-11-20、R89 の B 系の指摘への対応）。** 常駐部はまだ無く、どの基板にもロックされていないので、世代 1 の中身を変えた（世代は上げない。理由は §3-4）。
変えた点は §10 の表にまとめた。本文は変えた後の内容に直してある。コードは `mcu/bootcore`・`mcu/fwupdater`・`tools/fwimage` に入れ、ホストのテストで確かめた。**実機では何も確かめていない。**

用語：**常駐部** = 0x80000 の 8 KB に置く単独の実行ファイル（S3 で作る `mcu/resident`。まだ無い。純粋ロジックは `mcu/bootcore`）。
**アプリ** = feature `resident` でビルドした `mcu/netgd`。**配布用** = 常駐部の feature `dev` なし。

## 0. 要約

1. **常駐部は `WDT_MR` を書かない。** 復旧モードでは `WDT_CR` でカウンタを巻き戻すだけにする。`WDT_MR` は1回しか書けない [一次 §14.3] ので、
   常駐部が書くと「ウォッチドッグは永久に無効」がロック領域に凍る。親設計 §2-3 の「復旧モードに入るときだけ止める」は**この文書で取り消す**。
2. **アプリへ飛ぶ経路は3つ（通常・復旧の後・復旧に失敗して旧アプリへ）あるが、飛ぶときの状態は1つ。** 常駐部は `handoff()` 1つを通り、
   そこで §2 の表の値にそろえる。アプリは「リセット直後 ＋ クロックが 96 MHz ＋ FWS = 4 ＋ VTOR」だけを前提にしてよい。
3. **GPBR0 = アプリ → 常駐部の要求、GPBR1 = 常駐部 → アプリの報告。** GPBR1 が無いと、「FPGA が起きない → 復旧を要求 → 同じイメージなので書かない → また FPGA が起きない」
   でリセットが無限に続く。アプリは「この起動が自分の要求による復旧の後なら、もう要求しない」。
   常駐部は復旧を始める前に GPBR0 を 0 ではなく**「要求済み・進行中」の値**に書き換え、引き渡しのときに 0 にする。
   復旧の途中でリセットされても、次の起動は「要求は既に受けた」と分かり、もう一度は復旧せず、アプリにも `REQ` を報告する（§3-1、R89 の B6）。
4. **記述子 `"NGAP"` の版は 1 のまま永久に変えられない**（常駐部が版 1 以外を拒否するため [コード] `mcu/bootcore/src/app.rs:74`）。
   これから足す欄は、常駐部が読まない拡張ブロック `"NGAX"`（+0x120）に置く。
5. **4E のビットストリームの検査は常駐部に入れない。** アプリが「期待する CRC」を持ち、プレーン 1 の末尾の 4 バイトと比べる（起動時の費用はほぼ 0）。
   常駐部の凍結とは独立なので、**Supra の数字（R66）を待たずに常駐部を固められる**。やるかどうかはオーナーの判断（§7 の E4）。
6. 常駐部の版・世代・ビルドの種類は、常駐領域の末尾 16 バイト（0x00081FF0）の情報ブロックに置き、アプリが読んで `52 00` の「ブートローダーの版」に出す。
7. コードの調査で見つかった、取り決め以前の問題が3つある（§5 の K1・K7・K9）：更新プログラムのリセットが `SYSRESETREQ` で周辺回路が初期化されない、
   ボタンの3回読みが毎回の起動を 40 ms 遅らせる、`resident` のビルドに使えない更新プログラム 2.2 KB が入ったまま。

データシートの事実 [一次]：

- `WDT_MR`（0x400E1254）は「Read-write Once」。プロセッサリセットだけが元に戻す。リセット後は WDV = WDD = 0xFFF、WDRSTEN = 1、周期 約 16 秒で**動いている**。
  `WDT_MR` を書くとカウンタも巻き戻る。`WDT_CR`（0x400E1250、キー 0xA5、WDRSTT）は何度でも書ける。WDD = WDV の既定ではいつ巻き戻してもエラーにならない（§14.3、10165-10212 行、§14.4.2、10283-10340 行）。
- 既定の WDRPROC = 0 なので、ウォッチドッグのリセットはプロセッサと周辺回路の両方にかかる（§15.3.4.5、10605-10615 行）。
- `RSTC_CR`（0x400E1200、キー 0xA5）：PROCRST は「プロセッサとウォッチドッグ」、PERRST は「メモリ系を含む全周辺回路」を初期化する（§15.3.4.4、10555-10560 行）。
- `AIRCR.SYSRESETREQ` は「proc_reset_signal を出す」としか書かれていない（8017-8023 行）。周辺回路が初期化されるかは **[不明]**。
- GPBR は 8 本（`SYS_GPBR0..7`、0x400E1290〜）。リセット値の欄は「−」＝電源投入時の値は決まっていない（§19、表 19-1、12789-12809 行）。
- FWS と最高周波数：FWS = 3 で 84 MHz（VDDCORE 1.62 V）／96 MHz（1.80 V）。表は FWS = 3 まで（§42.9.8 表 42-55、48954-48960 行）。いまの FWS = 4 は 1 段の余裕。
- 正誤表：フラッシュに書いている間は FWS = 6（§46.1.1.3、§46.2.1.2）。MCK が 5 MHz 未満で FWS = 2 だと命令を読み誤る（§46.1.1.1）。

### 2-3 ウォッチドッグ

| # | 項目 | 飛ぶときの値 | 設定 | 確認 | ホスト | 実機 |
|---|------|--------------|------|------|--------|------|
| W1 | `WDT_MR` | **リセット値のまま、未書き込み**（WDV = WDD = 0xFFF、WDRSTEN = 1、動作中）。配布用の常駐部はどの経路でも書かない | 常駐部（書かないこと） | アプリが1回だけ書く。いまは WDDIS（`wdt.rs:10-14`）。将来有効にするのもアプリの自由 | 常駐部の逆アセンブルに 0x400E1254 を作る箇所が**無い**ことを CI で検査 | H9：常駐部経由で起動した後、`WDT_MR` の WDDIS が 1 に読める（アプリの書き込みが通った）。復旧の後の起動でも同じ |
| W2 | カウンタ | **`handoff()` の最初の動作として** `WDT_CR = 0xA5000001` で巻き戻す。そこからアプリへ飛ぶまでに **100 µs 以上**あける（`bootcore::boot::WDT_RESTART_TO_JUMP_US`。ピン・HSMCI・GPBR の後始末がそれより短ければ待つ）。アプリは飛んでから 約 16 秒以内に `WDT_MR` を書くか巻き戻す（いまは数 ms 後） | 常駐部 | アプリ | 模型の引き渡しは巻き戻しを最初に置く（`tests/common/sim.rs` の `jump`） | H9 |
| W3 | 復旧モードの間 | 常駐部が**上限の決まった間隔**で巻き戻す：SD の 1 セクタごと、EWP の 1 ページごと、LED の待ちの 200 ms ごと、カード待ちのループ 1 回ごと。どの待ちにもタイムアウトがあり、巻き戻しなしで 2 秒を超える区間を作らない | 常駐部 | — | 模型の `BlockRead`・`Flash` に「前回の巻き戻しからの経過」を数えさせ、上限を超えたら違反（§5 の B5） | H9：カードを抜いたまま 60 秒以上、復旧モードが続く（16 秒でリセットされない）。SD の読み取りを固まらせて（CMD 線を押さえる等）16 秒でリセットされ、また復旧に入る |

W2 を「最初に巻き戻し、100 µs あける」と決めた理由（R89 の B7）：後継の SAM（SAM4S、SAM E70 など）のデータシートには、
「`WDT_CR` で巻き戻した後、スロークロック 3 周期（約 92 µs）の間は `WDT_MR` を書いてはいけない」という注記がある **[二次：記憶による。SAM3U のデータシート 6430G にこの注記は無い]**。
アプリが最初にするのは `WDT_MR` の 1 回きりの書き込みになりうる（いまは起動の数 ms 後だが、取り決めとしては縛っていない）。
巻き戻しを飛ぶ直前に置くと、この窓にアプリの書き込みが入りうる。書き込みが無視されると `WDT_MR` は「1 回だけ」を使い切らずに残るのか、使い切って無効化に失敗するのかも分からない。
最初に巻き戻して間をあければ、SAM3U に同じ制約があっても無くても安全。**SAM3U に本当にこの制約があるかは H9 で確かめる**（常駐部経由の起動の直後に `WDT_MR` の WDDIS が 1 に読めること。あわせて、わざと巻き戻しの直後に書いた場合にどうなるかも見る）。

W1 をこう決めた理由：

- 常駐部が WDDIS を書くと、アプリの書き込みは黙って無視される（R60 の指摘）。いまのアプリは同じ値を書くので実害は無いが、
  「ウォッチドッグを使うアプリ」を将来作れなくなる。それを決める場所がロック領域の中、というのが良くない。
- 巻き戻し方式なら、常駐部の SD の初期化がある種のカードで固まっても、16 秒でリセットされる（GPBR0 は「進行中」になっているので、ボタンが押されておらずアプリが有効なら、次はアプリが起動し、`REQ` と結果 10 が報告される。§3-1）。常駐部のバグは SWD でしか直せないので、これは保険になる。
- 復旧中のウォッチドッグのリセットは、書き込み中の電源断と同じ扱い。`bootcore` の電源断の総当たり（R58・R61）がそのまま覆う。
- **EWP のタイムアウトでは、RAM のルーチンはフラッシュのコードに戻らない**（R89 の B5）。EWP の実行中はそのプレーンを読めず [親設計 §1-1]、呼び出し元はそのプレーンにあるコードなので、
  「FRDY が来なかった」と報告するために戻ると、戻った先の命令が読めずにフォールトする。タイムアウトしたら、RAM のルーチン自身が `RSTC_CR = 0xA5000005` を書く（または巻き戻しをやめてウォッチドッグに任せる）。
  どちらもページ書き込みの途中のリセットで、電源断の総当たりと同じ扱いになる。`Flash::ewp` は `Timeout` を返さない（`mcu/bootcore/src/flash.rs` のモジュールの説明）。SLB・GLB の間はフラッシュを読めるので、こちらは戻ってよい。
- 開発用（feature `dev`）は例外として WDDIS を書いてよい（既定では WDDBGHLT = 0 で、ブレークポイントで 16 秒止まるとリセットされるため）。情報ブロックのフラグで分かるようにする（§3-3）。

### 2-4 ピンと周辺回路

## 3. 常駐部とアプリが共有するデータ

### 3-1 GPBR0：復旧の要求

アプリ側の手順（新しい関数 `resident::request_recovery() -> !`、§5 の N1）：

1. 「この起動で既に要求した」なら何もしないで戻る（GPBR1 の `REQ` ビット、§3-2。**リセットの無限ループを止める規則**）。
2. 割り込みを止める。
3. `SYS_GPBR0 = 0x4352474E`。
4. `RSTC_CR = 0xA5000005`（PROCRST ｜ PERRST）。`SYSRESETREQ` は使わない（周辺回路が残るかどうかが [不明] のため）。

いつ要求するか（アプリの方針。常駐部には関係しない）：
4E で FPGA のロードが再試行の後も失敗し、エラーが一時的なもの（電源が来ていない）ではないとき。利用者の操作（将来の OGDM のサブコマンド、`netgd-fwupd` の「SD から入れ直す」）。
**6.0 の「`NETGD.BIT` が無い・壊れている」では要求しない**（アプリのイメージを書き直しても直らない。R66 の LED 5〜8 のまま）。

常駐部側（`bootcore::boot::decide`・`Request`）。GPBR0 の値は 3 通りに読む：

| GPBR0 | 意味 | 復旧に入るか | 復旧の前に書く値 | `handoff()` で書く値 | 報告 |
|-------|------|--------------|------------------|----------------------|------|
| `0x4352474E`（`"NGRC"`、アプリが書く） | 新しい要求 | 入る | `0xBCADB8B1`（進行中） | 0 | `REQ` |
| `0xBCADB8B1`（常駐部が書く。合言葉の全ビット反転） | **要求された復旧の途中でリセットされた** | これを理由には**入らない**。アプリが無効か、ボタンが押されていれば入る（そのときは書き換えず、進行中のまま） | — | 0 | `REQ`。アプリが有効でそのまま起動するときは `result` = 10 |
| それ以外 | 要求なし | アプリが無効か、ボタン | — | 書かない（常駐部のものではない） | — |

「進行中」の値を置く理由（R89 の B6）：以前の案は復旧の前に 0 を書いていた。すると、復旧の途中のリセット（SD の初期化が固まって 16 秒後にウォッチドッグ、EWP のタイムアウト、リセットボタン）で
「アプリが要求した」という事実が消える。`REQ` は引き渡しのときの GPBR1 にしか入らないので、次の起動は普通の起動になり、アプリはまた要求する。
「要求 → ハング → 16 秒 → アプリ → 要求 → …」が電源を切るまで続く。進行中の値が残っていれば、次の起動はそれを見て復旧をやり直さず、`REQ` を報告するので、アプリの規則 X6 がそのまま効く。

- 進行中の値は合言葉と 32 ビットすべてが違い、0 でも全 1 でもなく、上位 16 ビットは GPBR1 の目印（`0x4EB1`）でもない。
- 進行中のまま電源が切れても同じ扱いになる（GPBR はバックアップ電源の領域。VDDBU が落ちれば不定値に戻り、「要求なし」と読まれる）。
- アプリが無効で進行中のとき（書き込みの途中のリセット）は、復旧するしかない。成功すれば `REQ` を付けて起動するので、アプリはその回には要求しない。
  この経路で復旧が何度も途中で止まる場合（毎回ハングする）、止める手段は無い（アプリが無いので、ほかにすることが無い）。
- 次の普通のリセットや電源投入では GPBR1 に `REQ` が無いので、アプリはまた 1 回だけ要求できる。

### 3-2 GPBR1：起動の報告

```
 31        24 23        16 15         8 7          0
+------------+------------+------------+------------+
|    0x4E    |    0xB1    |   flags    |   result   |
+------------+------------+------------+------------+
flags  bit0 BTN     ボタンが押されていたので復旧に入った
       bit1 REQ     GPBR0 の要求で復旧に入った
       bit2 WROTE   この起動でフラッシュを書いた
       bit3 LOCKED  最後の GLB で領域 0 のロックビットが 1 だった
       bit4 SLB     この起動で SLB を出した
       bit5 UNSEALED 封印されていないアプリを受け入れた（開発用だけ）
       bit6 LOCK_UNKNOWN 最後の GLB が失敗した。領域 0 がロックされているかは分からない（LOCKED は 0。同時には立たない）
       bit7         0（予約）
result 0            復旧を試みていない（通常の起動）
       1            復旧が終わった（書いた、または同じイメージなので書かなかった）
       2〜9         復旧に失敗し、有効な旧アプリを起動した。値は LED の回数と同じ（§6-2）
       10           GPBR0 が「進行中」だった：要求された復旧がリセットで中断された。今回は復旧していない。必ず REQ と一緒（LED には出さない）
```

- 上位 16 ビット `0x4EB1` は目印。電源投入直後の GPBR は不定 [一次] なので、目印が合わなければアプリは報告なしとして扱う（プローブから直接起動した場合もこれ）。
- アプリの使い方：ログに出す。`REQ` が立っていれば、この起動では `request_recovery` を出さない。報告が無い（目印が合わない）ときも出さない（答える常駐部が無く、同じアプリがまた起動するだけ。`boot::request_allowed(None)` は false）。`LOCKED` が 0 で配布用の常駐部なら、警告として `netgd-fwupd` に見せる。`LOCK_UNKNOWN` が 1 なら「ロックの状態を読めなかった」と見せる（「ロックされていない」とは言わない）。
- アプリは GPBR1 を消さなくてよい（常駐部が毎回書くので古い値は残らない）。

### 3-3 常駐部の情報ブロック（0x00081FF0、16 バイト、ロック領域の末尾）

| オフセット | 内容 |
|-----------:|------|
| 0 | マジック `"NGRS"` |
| 4 | バイト 0：**インターフェース世代**（この文書 = 1）／バイト 1：フラグ（bit0 開発用、bit1 自己ロックあり、bit2 ボタンあり、bit3 LED あり、bit4 `WDT_MR` を書く）／バイト 2-3：`layout >> 8`（`0x0020`） |
| 8 | 常駐部の版 `major << 16 | minor << 8 | patch` |
| 12 | 常駐領域全体（0x80000〜0x81FFB）の CRC-32。アプリのトレーラと同じ規則（`app.rs:112-114` の `check_trailer` がそのまま使える） |

- 使っていない領域は 0xFF。CRC は `fwimage` が埋める（§5 の F3）。配布する常駐部のバイナリは必ず 8,192 B。
- アプリは普通のメモリ読み出しで読む（EEFC は使わない）。マジックが違う、または世代が 0 なら「常駐部の版は不明」。
- 出す場所：起動時のログ、`52 00` の先頭の語（いまは 0.0.0。`ide.rs:2336-2343`）、OGDM の版の応答の予約バイト（`ide.rs:2195-2209`）。
  CRC の照合（8 KB で 約 1 ms [推測]）は起動時にはせず、`netgd-fwupd` から頼まれたときだけにする（2E はコードの空きが少ない）。

### 3-4 世代の規則

- **世代は、この文書の §2・§3 のどれかを互換でなく変えたときにだけ上げる。** 常駐部の版（バグ修正）とは別。
- アプリは「自分が知っている最大の世代」と「動くのに要る最小の世代」（拡張ブロックの `min_gen`、§3-5）を持つ。
  常駐部の世代が自分の最小より小さい → 起動はする（止まる理由が無い）、該当する機能だけ使わない、ログと `netgd-fwupd` に出す。
  常駐部の世代が自分の知っている最大より大きい → 世代 1 の取り決めは守られていると仮定する（**後の世代は世代 1 の §2 を壊さない**。壊すなら `layout` か `APP_BASE` を変え、形式 3 の語 9 で古いアプリを拒否する）。
- 逆向き（常駐部がアプリの世代を知る）は要らない。常駐部がアプリについて読むのは記述子の語 0・4・8・28 とベクタ 4 語とトレーラだけ。
- **凍るもの（常駐部をロックした後は SWD でしか変えられない）**：`APP_BASE`、`layout`、記述子の位置（+0x100）・長さ（32 B）・版（1）・語 0/4/8/28 の意味、
  トレーラの規則、ベクタの検査、GPBR0 の合言葉と「進行中」の値、GPBR1 の形（フラグ 7 個と `result` 0〜10）、情報ブロックの位置と形、OGFW 形式 3 のヘッダ、ファイル名、LED の回数、
  書き込みを伴う復旧の回数の上限（§5 の Y7）、§2 の全項目。
- **R89 の対応で世代 1 の中身を変えたが、世代は 1 のまま、記述子の版も 1 のまま。** 世代は「ロックされて出回っている常駐部とアプリの間で互換でない変更」を数える番号で、
  いまは常駐部が 1 つも存在しない（S3 の前）。変更前の世代 1 を実装した常駐部はどこにも無いので、区別する相手がいない。上げると、最初に出荷する常駐部が世代 2 になり、
  「世代 1 の常駐部」という存在しないものにアプリが備えることになる。記述子（`"NGAP"`）は今回まったく変えていない。
  アプリから見える変更は GPBR1 のビット 14（予約 → `LOCK_UNKNOWN`）と `result` 10 の追加だけで、どちらも「予約は 0、読むときは無視」「2 以上は失敗」という元の読み方と矛盾しない。

## 4. 起動のたびのロックの手順と、4E のビットストリーム

### 4-1 配布用の常駐部の手順

```
クロックを 96 MHz に、FWS = 4
1. GLB（語 0x5A00200A、fcr.rs の GLB_FARG）→ FRR のビット 0。どのコマンドも、FCR に書く前に FSR を 1 回読む（古い FCMDE・FLOCKE を消す）。
   FRDY を見た読み取りで FCMDE が立っていた、または FRDY が来なかった → GLB は失敗（「分からない」）
2. GLB が成功してビット 0 が 0 なら：FWS = 6 → SLB 0（語 0x5A000008）→ FSR（FRDY を見た読み取りで FCMDE・FLOCKE も取る）→ FWS = 4 → GLB をもう一度。
   GLB が失敗したら SLB は出さない
3. 結果を覚える（LOCKED、SLB、LOCK_UNKNOWN）。**ロックできなくても、読めなくても、起動は続ける**（止めると、ロックビットの不調で文鎮になる）
4. ボタン・GPBR0 → decide → アプリの検査 → handoff()（GPBR1 に LOCKED・SLB・LOCK_UNKNOWN を入れる）
```

- GLB・SLB は RAM の同じ1つの関数から出す（`EEFC_FCR` に書く場所を1つにする。親設計 §3-2）。SLB・GLB の間はフラッシュを読める [一次 §20.4.3.4] ので必須ではない。
- **SLB 0 は CLB 0 と 1 ビット違い**（`fcr.rs:53-57`、R61 の判断）。SLB を出すのはロックが外れているときだけ（普通は一生に1回）なので、
  化ける機会はその1回。化けても「外れたまま」で、手順 2 の読み直しで分かり、次の起動でまた SLB を出す。GLB（毎回）は SGPB 0 と距離 2。
- SLB の途中の電源断：ロックビットは不定 → 次の起動の手順 1・2 で直る。
- SLB のときも FWS = 6 にする（正誤表は「フラッシュに書くとき」としか言っていないが、ロックビットも同じ NVM なので安全側 [推測]）。
- 手順 1 の時間は [不明]。H2 の測定に含める（FPGA の起動を遅らせる側に入る）。
- GLB に引数 0x20 を入れても FRR が同じか、SLB の引数 0 が「領域 0」か、は実機の確認項目のまま（R59）。

### 4-2 開発用（feature `dev`、D4）

SLB を出さない（GLB は出して報告してよい）。封印されていないアプリを受け入れる（`app.rs:73-88`）。`WDT_MR` に WDDIS を書いてよい。
情報ブロックのフラグの bit0 = 1。**アプリは bit0 = 1 を見たら、ログと `netgd-fwupd` に「開発用の常駐部」と出す**（配布物に混ざったときに気付けるように）。
開発用で確かめられないもの：ロック、W1（`WDT_MR` を書かないこと）、封印の検査。これらは配布用のビルドを SWD で入れて確かめる（H4・H9）。

### 4-3 4E のビットストリーム（R60 の指摘）

事実：4E ではトレーラ CRC はプレーン 0 だけを覆う。プレーン 1 のビットストリームは、SD 復旧で書いた直後に 1 回照合されるだけ（`update.rs:354-355`）。

何が起こりうるか：

| 場面 | いま気付けるか |
|------|----------------|
| (a) `0xF9` の更新でコードは新しく、ビットストリームは古いまま（片方だけ送った、途中で止まった） | **気付けない**。古い設計は正しい CRC を持つので FPGA は起きる。記述子の `bs_len`・`bs_raw_len` が偶然違えば LZMA が失敗する程度 |
| (b) プレーン 1 の書きかけ | Cyclone II のコンフィグの CRC（nSTATUS）と LZMA の復号エラーで、ほぼ気付ける [推測] |
| (c) 置いてある間のビット化け | 同上 |

4E の基板は v5.5（Cyclone II）だけで、6.0 は 2E。2E ではビットストリームはイメージの中（トレーラが覆う）か SD の `NETGD.BIT`（自前の CRC、R66）なので、**この穴は v5.5 だけのもの**。

案：

| 案 | 内容 | 起動時の費用 | 常駐部 | 評価 |
|----|------|--------------|--------|------|
| V0 | 何もしない | 0 | 変更なし | (a) が残る |
| V1 | 常駐部がプレーン 1 の CRC も計算する | +約 7 ms（49.6 KB、4 ビット表）[推測]。FPGA の起動がそのぶん遅れる | **凍る**。失敗したとき常駐部にできるのは SD 復旧だけで、それはアプリが要求しても同じ | 勧めない |
| V2 | アプリが FPGA のロードの前にプレーン 1 の CRC を計算する | +約 7 ms [推測] | 変更なし | (a)(b)(c) 全部。遅れが気になる |
| **V3（推奨）** | **印（スタンプ）**：ビットストリームの画像の末尾 4 B に自身の CRC-32 を置く（アプリのトレーラと同じ規則）。アプリは拡張ブロックの `bs_stamp` とその 4 B を比べるだけ。全体の CRC は、失敗したときと `netgd-fwupd` の診断のときだけ計算する | **ほぼ 0**（1 語の比較） | 変更なし | (a) と (b) を確実に、(c) は FPGA の CRC に任せる |

V3 の中身：

- リンカ：`.flash1` の後ろに詰め物と 4 B の `.bs_crc` を置き、512 の倍数で終える（`.image_pad`・`.image_crc` と同じ作り。`link/sam3u4e_resident.x:43-48`）。
- `fwimage`：`seal`・`build` が ビットストリームの CRC → `.bs_crc` と拡張ブロックの `bs_stamp` → 記述子 → イメージのトレーラ、の順に埋める（`fwimage.py:229-242`・`413-443`・`448-`）。
  `inspect` は「コードの `bs_stamp` とビットストリームの画像の末尾が同じか」を見る。**2 つの画像の組み合わせを送る前に PC で確かめられる**のが一番の利点。
- アプリ：`bs_stamp != 0` かつ記述子のビットストリームの番地が 0x00100000 のとき、ロードの前に 4 B を比べる。違えば FPGA を流さず、LED と GPBR0 の要求（§3-1 の規則つき）。
- 更新プログラム・常駐部：変更なし。種別 1 のペイロードの中身が変わるだけで、ヘッダの `payload_crc` はそのまま全体を覆う。

待つもの：なし。Supra の大きさ（R66）で決まるのは 6.0（2E）の置き場所で、V3 は 4E のプレーン 1 だけの話。6.0 が SD になっても `bs_iface` の欄は同じ意味で使える。

### 4-4 GLB が失敗したとき（R89 の B12）

以前の案は「GLB の失敗は全ビット 1（全部ロック）と読む」だった。安全側に見えるが、2 つの嘘になる：
(1) 領域 0 が `LOCKED` と報告され、SLB を試さないので、実際にはロックされていない基板が「ロック済み」に見える。
(2) 復旧の前の検査がアプリ領域を「ロックされている」と読み、GLB が直らない限り**復旧を永久に拒否する**。アプリが無効なら文鎮になる。

決めたこと（`Flash::lock_bits` は `Option<u32>` を返し、失敗は `None`）：

| 場面 | GLB が失敗したら | 理由 |
|------|------------------|------|
| 起動のたびのロック（§4-1） | SLB を出さない。`LOCKED` = 0、`LOCK_UNKNOWN` = 1 を報告。起動は続ける。次の起動でまた GLB から | ロックされているかもしれない領域に SLB を出すと、CLB に化ける機会を増やす。害の無いコマンドを断ったばかりのコントローラに書き込み系を出さない |
| 復旧の前の検査、**有効なアプリがある** | その回は書かずにやめる（`LockUnknown`、`result` = 6）。旧アプリを起動する。次の回（次の起動、次の要求）にまた GLB を読む | 途中の領域だけがロックされていると、先頭を消した後に本体を書けず、動いていたアプリを失う。分からないまま賭けない |
| 復旧の前の検査、**有効なアプリが無い** | 書き進める | 失うものが無い。ロックされたページへの EWP は FLOCKE で中止され、フラッシュは変わらない（`Locked` で止まる） |

一時的な失敗なら次の回に直る。恒久的に GLB が失敗する基板では、有効なアプリは SD から更新できない（アプリは動いている）が、アプリを失った基板は復旧できる。
`fwupdater`（`0xF9` の更新）は GLB の失敗をそのコマンドだけ `Locked` として返す（ホストがやり直せる。覚えない）。

| FPGA のロードの失敗、`NETGD.BIT` の問題 | アプリ | LED（`PsError::code()`、R66 の 5〜8） |

### 6-2 回数と、見分け方

常駐部の `result`／LED の回数は親設計 §2-3 の案のまま：2 カードなし、3 ファイルなし、4 読み取りエラー、5 ヘッダか対象が違う、6 アプリ領域がロックされている（またはロックビットを読めず、有効なアプリを守った）、7 書き込みエラー、8 CRC 不一致、9 書いた後の検査に失敗。
`result` 10（要求された復旧がリセットで中断された）は LED には出ない（常駐部はすぐアプリを起動する）。アプリのログと `netgd-fwupd` で見せる。

問題：アプリの回数（`PsError::code()` は 1 から、R66 は 5〜8）と**数が重なる**。同じ LED で「5 回」が 2 つの意味になる。
案：常駐部の点滅は、毎回の組の前に 1 秒の長い点灯を入れる（アプリは 200 ms の点滅だけ。`cyclone.rs:193-204`）。回数の表は 1 つにまとめて `INSTALL.md` に置く。
LED のピンが分からない基板（6.0、H5 の前）の常駐部は LED なしでビルドし、情報ブロックのフラグ bit3 = 0 にする。その場合の「アプリが無効」は、外からは「何も起きない」に見える。
**6.0 用の常駐部をロックするのは、LED かボタンのどちらかが分かってから**にするのが安全（E6）。

## 7. オーナーに決めてほしいこと

| # | 決めること | 推奨 | 理由・代償 |
|---|-----------|------|-----------|
| E1 | ウォッチドッグ：常駐部は `WDT_MR` を書かず、復旧中は巻き戻す／常駐部が WDDIS を書く（親設計の元の案） | **書かない** | 書くと「無効」がロック領域に凍る。代償は巻き戻しの呼び出し（数十 B [推測]）と、W3 の実機の試験 |
| E2 | 引き渡しの状態を「3 つの経路で同じ」にする（`handoff()` で元に戻す）／復旧の後は必ずリセットしてから通常の経路で起動する | **`handoff()`**。R61 の「成功したらリセットせずに飛ぶ」を保つ | リセット方式は、ボタンが押しっぱなしのときに「復旧 → リセット」が続かないよう GPBR にもう 1 つ合図が要り、「同じイメージなので書かない」の後は結局そのまま飛ぶしかない。代償は [R] の試験が 3 経路ぶん要ること |
| E3 | GPBR1 の報告と情報ブロック（§3-2・3-3）を世代 1 に入れる | **入れる** | 入れないと、復旧の要求のループを止められず、6.0 で失敗の理由が見えず、アプリが常駐部の版を知れない。常駐部に 約 60〜100 B [推測] |
| E4 | 4E のビットストリーム：V0 何もしない／V2 アプリが毎回 CRC／V3 印を比べる | **V3**。ただし優先度は低い（v5.5 だけ、常駐部の凍結と無関係） | V3 は `fwimage`・リンカ・アプリの変更。起動は遅れない。V0 でも Cyclone II の CRC で書きかけは分かるが、新旧の取り違えは分からない |
| E5 | 拡張ブロック `"NGAX"`（+0x120）を今のうちに入れる | **入れる**（32 B） | 記述子の版が凍るので、将来の欄の置き場が要る。E4 で V0 を選んでも `min_gen` と `bs_iface` に使う |
| E6 | 6.0 用の常駐部を、LED もボタンも分からないままロックしてよいか | **しない**（H5 の後） | 分からないままだと、復旧に入る手段が「アプリが無効」と GPBR だけで、失敗が外から見えない |
| E7 | リセットの出し方を `RSTC_CR`（PROCRST ｜ PERRST）に統一する | **する**（S5 の更新プログラムから） | `SYSRESETREQ` で周辺回路が残るかが [不明]。常駐部は残っていても動くように作る（Y4）が、試験する状態を減らせる |
| E8 | LED の見分け方（常駐部は長い点灯を前置き）と回数の表 | D6 と一緒に、ピンが分かってから | 常駐部に入れると変えられない |
| E9 | `resident` のビルドから形式 2 の更新プログラムを今すぐ外す（N5） | **外す** | 2E で 約 2.2 KB 戻る。S5 までは `resident` のビルドに更新の経路が無い（今も拒否しているので、動作は変わらない） |

## 8. 実機で確かめること（追加分）

親設計 §6 の H1〜H7 に足す。どれも SWD のある v5.5 でできる。

| # | 内容 | 段階 |
|---|------|------|
| H8 | **[R]**：開発用の常駐部から、アプリの `__pre_init` で止めて、PMC（MOR・PLLAR・MCKR・SR・PCSR0・SCSR）、EEFC0/1 の FMR、PIOA/B/C（PSR・OSR・ABSR・PUSR）、HSMCI（MR・SR・IMR）、NVIC（ISER・ISPR）、SysTick、VTOR、MSP、PRIMASK を読む。通常・復旧成功・復旧失敗からの旧アプリの 3 経路で比べる。常駐部なし（プローブから直接）とも比べ、違いが §2 のとおり（クロックと FWS だけ）であること | S3・S4 |

## 9. この文書が決めていないこと
